# ADR-0006: Guardrails without organisation-level policy
- Status: Proposed
- Date: 2026-10-01
- Related: ADR-0001, ADR-0005, ADR-0008, ADR-0012

## Context
Azure Policy, AWS SCPs and GCP org policy let a root enforce rules that every child inherits. On
OVHcloud we found IAM allow/deny policies with tag conditions, resource groups, and no inherited
preventive layer (_UNVERIFIED that none exists; spike required_). A guardrail that exists only in the
pipeline is bypassed by anyone with console access, so claiming "enforced" would be dishonest.

## Options considered
1. Pipeline-only policy checks.
2. Pipeline checks **plus** IAM-policy-based restriction of humans to least privilege.
3. 2 plus a scheduled **detective** scanner that reports out-of-policy resources.
4. Wait for the platform.

## Decision (proposed)
Option 3, with three explicit guardrail classes, each labelled in docs:

| Class | Mechanism | Strength |
|---|---|---|
| **Preventive (platform)** | IAM policies/deny rules and tag conditions generated by `identity-baseline`; humans get read + break-glass, automation applies | Real, but only as strong as IAM allows |
| **Preventive (pipeline)** | OPA/conftest on `tofu show -json` plan output; apply blocked on violation; separate plan and apply jobs | Bypassable outside the pipeline |
| **Detective** | `tools/` scanner run on a schedule: lists projects/resources via API, compares to desired state and policy, reports drift and non-compliance (JSON + issue/MR comment) | Never blocks; report-only |

- Policies are Rego in `policies/`, each with a test file and a metadata header (id, severity, class,
  profile membership — ADR-0012).
- A violation message always names the policy id and a fix; docs have one page per policy.
- Auto-remediation is **off** by default; the scanner never deletes (ADR-0004 safe-by-default).
- Docs state the bypass explicitly: "console users with project admin rights can step outside the
  pipeline; the detective scanner will report it, not prevent it".

## Consequences
- Honest posture; fits the "unofficial, not CAF" positioning (ADR-0001).
- The scanner is a second product to maintain and needs API credentials with read scope.

## Counterpoints
- Detective-only controls on a "landing zone" may disappoint compliance-driven adopters; the profiles
  (ADR-0012) say precisely what is and isn't covered.
- OPA vs Trivy custom checks vs Checkov: single engine proposed (OPA) to avoid duplicated rules.

## Verification
- Spike: IAM `deny` with tag conditions across two projects; does a deny on project-creation or on
  public-IP actions work as a de-facto guardrail?
- Spike: API list calls needed by the scanner and their rate limits (`api_rate_limits` doc exists).
