## Choices made here (not fixed by the spec set)

- Signatures (plan.md and data-model fix none): `Explain(source, code, detail string) (string, error)` and `ExplainError(err error) (string, error)`. `ExplainError` takes the source from the error's own type, without unwrapping: `*AnswersError` is `configure`, `*stacks.ManifestError` is `generated` (T017 returns it unwrapped). Anything else, a wrapped error included, has no source and returns an error, never the raw text (FR-004: no silent fallback). A current manifest that does not decode is `CURRENT_MANIFEST_INVALID` under `configure`, which T020 raises through `Explain`; passing that decoder error to `ExplainError` would wrongly pick `generated`, so the doc comment says the `ManifestError` case is the generated manifest only.
- The four command codes of data-model (`CURRENT_MANIFEST_INVALID`, `STAGING_SYMLINK`, `STAGING_WRITE`, `STAGING_NOT_DURABLE`) become constants in `messages.go`, so the completeness test's parse of the package finds all twelve `configure` codes; T020 raises them.
- Text: the plain sentence and the next action are the contract's, verbatim, each ending in its own full stop; the line is `configure: <CODE>: <detail>. <sentence> Next: <action>`, which is data-model's template with the sentence's full stop. Every unreachable `generated` code is listed by name and points at the one tool-defect entry; no default entry exists, so the completeness check stays meaningful.
- One line: a detail holding a control character (a file path with a newline) is printed Go-quoted, so the refusal stays one line (FR-004 "prints one line").
- The completeness check lives in the test file: it parses `tools/internal/stacks/manifest.go` and the non-test files of `tools/internal/configure` for exported `Code*` constants with a string value (block and single declarations), fails on a parse error, on zero codes for either source, on a missing entry (naming source and code), on an entry with an empty sentence or action, and on an entry whose code no parse found (a stale entry).

## Harness gaps

- `ReadAnswers` still returns a plain wrapped error for an I/O failure other than a missing, non-regular or oversized file (EACCES, EIO; T016 gap). `ExplainError` refuses it (no source), so it is never printed raw, but the catalogue has no entry for it: the command (T020) has to decide what it prints. Deferred to T020, which owns the command's output; adding an entry is a contract change.
- The catalogue text is compared with contracts/checks.md by a host script and review, not by a test: a test would read `specs/` and widen `test:configure`'s inputs.

## Maintainability

1. Locality: yes, only `messages.go` and `messages_test.go`.
2. Change surface: one requirement, two new files (~130 and ~390 lines); the test is long because each case has a control.
3. Duplication: the test reuses T016/T017 helpers (`answersFixture`, `answersReadFile`, `answersPadded`, `exportGateCases`, `exportGateAnswers`); the Go-source parse is new (T016's `answersForbiddenUses` walks imports and calls, not constants).
4. Second way: no; `Explain` is the one formatter, `ExplainError` only picks the source.
5. Coupling: `messages.go` names the 18 `stacks.Code*` constants, which `export.go` already imports; the test parses `../stacks/manifest.go`, an existing input of `test:configure`.
6. Abstraction: no; the decoder errors are used as returned.
7. Debt for green: no; quoting a detail with a control character is FR-004's one line, tested with a real path.
8. Legibility: the catalogue reads as the contract table, one entry per key.

Easier: T020 prints any refusal with one call, and a new decoder code turns a test red until it has an entry. Harder: a new `Code*` constant in `tools/internal/stacks/manifest.go` now needs a catalogue entry here.
