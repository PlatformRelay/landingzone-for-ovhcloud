## Decisions

Recorded per the dispatch; OVHcloud behaviour is UNVERIFIED unless a source settles it.

- **Tag key with `:`**: allowed. Source: kb api/v2/iam.json, iam.resource.AddTag key
  `'^[a-zA-Z0-9_.:/=+@-]{1,128}'` (read 2026-10-16, verified); provider docs
  resources/iam_resource_tags.md says the same. The PUT body (iam.resource.Resource.tags) is
  assumed to follow AddTag's pattern (believed); the checker gates keys and values on it.
- **Is an S3 bucket listed as an IAM resource?** UNVERIFIED. No source settles it; the bucket
  operations' IAM actions are `publicCloudProject:apiovh:region/storage/*` (kb api/v1/cloud.json,
  read), which suggests buckets are checked as parts of the project, not as resources of their
  own (believed). So the likely live result for the write is `blocked (no owned target)`: T027
  then learns the read's URN only, and the write's question stays open (see *Harness gaps*).
- **Bucket URN form**: UNVERIFIED; the root publishes
  `urn:v1:eu:resource:storageS3:<project>/<bucket>` (T033's fake form; the provider exports no URN
  for a bucket, provider docs resources/cloud_project_storage.md, read). The check writes only to a
  resource the listing shows under the bucket's name with exactly that URN, and records every URN
  the listing showed (`bucket_urns_listed`), so T027 learns the form either way.
- **The account URN** comes from `data "ovh_me"` `urn` (provider docs data-sources/me.md); its
  form `urn:v1:eu:resource:account:<account>` matches the captured admin policy (spec 005
  evidence/T042.md; the capture matched the check's account regex, verified 2026-10-16). The data
  source reads account details into the probe's encrypted state, which stays outside the checkout.
- **The read**: `account:apiovh:iam/policy/get`, GET /iam/policy/{policyId} on the identity's own
  policy (kb api/v2/iam.json iamActions, read 2026-10-16), as T033 fixed.
- **Tags the write sends**: the listed tags plus the run's key, as T033's header fixes. Provider
  docs say `ovh:`-prefixed tags cannot be set through the API; whether a PUT that sends them back
  unchanged is refused is UNVERIFIED (a 400 shows as `outage` in the record; README row 11 says so).
- **Observe fails on any blocked result** (the record is kept), as the token-residual check does.
- **The two identities bind nothing** (Options.Bind unused): each is the admin's own disposable
  client, and a bind would take a token of its own.
- **Never tag the retained project**: the root has no IAM tag resource (tftest
  `creates_only_the_bucket`, mutant project-tagged KILLED); Validate refuses a bucket_urn equal to
  project_urn or account_urn; the write goes only to the listed bucket URN; cleanup removes the key
  only from a resource named the bucket whose URN ends in it.
- **Answer fields against every secret**: each answer's actions are dropped when any of the run's
  checkers (admin and both clients) carries them (`APIChecker.Carries`).
- **Both instants**: each attempt has `at` and `answered_at`; the policy age runs from the policy's
  createdAt (OVHcloud's clock; the create's answer instant when absent) to the send (this host's
  clock): it cannot overstate the age while the clocks agree; a host clock ahead of OVHcloud's
  overstates it by the skew (review r1).
- **Policy acceptance**: whether OVHcloud accepts a policy pairing `account:apiovh:iam/*` actions
  with a project URN (and `publicCloudProject:apiovh:get` with it, `account:apiovh:me/get` with the
  account URN) is UNVERIFIED; a refusal is recorded as `setup` and Observe stops before any probe call.
- **Listed text**: listed URNs reach the record only when they hold no secret of the run; tags of
  another shape than iam.resource.AddTag's are dropped in the checker (a key of the right shape is
  kept with an empty value, so cleanup still removes the run's key, review r2) and mark the resource
  partial, which is then no write target (review r1).
- **Propagation within a policy**: a control's success is taken to mean the probed actions of the
  same policy are in effect too; UNVERIFIED (review r2). A partly propagated policy would show as an
  attributable 403 and could be read as the other URN; T027 can repeat the run to rule it out.
