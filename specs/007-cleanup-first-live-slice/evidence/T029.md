- Smallest coherent change: (a) `lockRun` (`files.go`) puts `run.lock` in the run's directory by a hard link of a fully written temporary (exclusive; a lock is never seen half-written), naming its holder's pid and start time (`/proc/<pid>/stat` field 22). A lock whose pid is gone, or whose pid now runs with another start time, is stale: it is removed and the link tried once more. Every take, the stale check and removal included, runs under a non-blocking `flock(2)` of the run directory, which the kernel drops when its holder dies; a take that finds it held refuses at once (review round 2: a waiting take could hang behind a stopped process). The temporary is synced before the link (review round 1: the first design renamed a stale lock aside and could leave two holders with three processes). The lock is read with `O_NONBLOCK|O_NOFOLLOW` and must be a regular file. A live holder, or a lock that cannot be read (FIFO, symlink, no pid), refuses (`run-locked`) naming the run. Nothing is judged by age. `Probe.Start` takes the lock right after `claimDir`; `Probe.Cleanup` takes it before reading anything of the run. Both release it on every return (`releaseRun` in a defer), and `retire` removes it after `probe.env`. (b) `retireEmptyClaim`: a run directory with no `probe.env`, no entry but the lock and `.write-*` temporaries, and no baseline recovery copy is retired by a plain `--cleanup`. This goes through `Probe.Cleanup`, and through `RetireEmptyClaim` from `lz-live` before it reads `probe.env`. Anything else is refused (`record`) and nothing is removed. The `unreconciled-run` refusal no longer sends the owner to manual removal.
- Scope note: `tools/cmd/lz-live/probe.go` is touched although the task line names only `runner.go` and `files.go`. `lz-live probe --cleanup` reads `probe.env` (`ProbeRoot`) before it builds a `Probe`, so without a call there an empty claim never reaches `Probe.Cleanup`. Adding that branch to `probe` raised its complexity above the baseline (28 → 30). The cleanup branch therefore moved into `cleanupTarget` (same statements, plus the claim call), which brings `probe` to 26. `tools/harness/complexity-baseline.txt` was lowered to 26: a downward rewrite, as the gate asks for, not a widening. Docs: `docs/how-to/run-the-first-slice.md` (the refusal paragraph, the no-lock paragraph replaced by the lock, shifted `runner.go` line citations), and blob pins plus `last_verified` in `set-up-a-fresh-account.md` (files.go) and `respond-to-an-incident.md` (probe.go).
- Files: `tools/internal/live/{files.go,runner.go}`, `tools/cmd/lz-live/probe.go`, `tools/harness/complexity-baseline.txt`; tests `tools/internal/live/run_lock_test.go`, `tools/cmd/lz-live/probe_claim_test.go`; the three docs; `tasks.md`, `loop.md`, this file.
- Decisions taken here (agent, fail-safe reading of the task text): a `.write-*` temporary counts as part of the claim: retire already treats it as the run's own (T027), and with no `probe.env` it can only be `probe.env`'s or the lock's temporary. A claim cleanup with `--accept-lost-baseline` is not retired, in `lz-live` and in `Probe.Cleanup` alike (review round 1): it keeps today's error, because `probe.env` is missing. A lock that cannot be parsed refuses (manual removal) and is never taken over. A start whose lock is refused leaves the claimed directory to the holder. The task's "no baseline" is read as no recovery copy (review round 2): `retire` removes the recovery copy before `probe.env`, and every passing run keeps its record copy in the run record, so a retire cut short after `probe.env` leaves the record copy beside a directory for which nothing exists in OVHcloud; refusing on it would block every start until manual removal. A start killed before `probe.env` has written neither copy.

## Learnings

Class: guidance (two lessons appended to loop.md *Lessons*).
- A lock taken by an exclusive create needs its stale takeover serialised by something the kernel drops on death (a non-blocking `flock` of the directory); rename-aside plus a check still lets a third process in.
- A retire that removes files in order leaves every prefix of that order after a crash: check the cleanup accepts each cut point.
