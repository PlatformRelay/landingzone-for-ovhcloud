# T026 — Discard pending terminal input before the `--accept-lost-baseline` prompt (US3)

- Feature: `specs/007-cleanup-first-live-slice/` · branch: `lane-007` · pre-task: `63b2153` · started: 2026-10-19
- Satisfies: FR-007 (owner recovery `--accept-lost-baseline`: the owner types the run id back at the controlling terminal) · US3 · coordinator brief 2026-10-19 (the owner's live session, about 22:10) · constitution: V (fail closed)
- Defect (owner's report, believed; not re-observed live): `live:probe --cleanup <id> --accept-lost-baseline` for 8 runs in a shell loop. The prompt read lines already in the terminal's input (earlier keystrokes, an arrow key `^[[D`), so every later answer was read one run late: runs 2 and 3 refused without waiting, run 4 refused although its id was typed correctly. Nothing was deleted (fail-safe), but the gate was unusable for a list of runs.
- Root cause (verified by reading `tty_linux.go` at `63b2153` and by the red below, 2026-10-19): two stacked faults. (1) No flush: the kernel's input queue kept whatever was typed before the prompt. (2) `newTTY` started its reader goroutine at once, so it read the first pending line before any prompt existed and held it for the next `read`; a flush alone would not have dropped that line.
- Smallest coherent change: the reader reads only when a prompt asks (`asks` channel), so pending input stays in the kernel; `ReadLine` and `ReadSecret` discard it (`TCFLSH`/`TCIFLUSH` on the `/dev/tty` fd) before showing the prompt, then read one line; `bufio` is reset per prompt, so nothing read past one line is kept for the next. The refusal says what was read (`readSummary`: length in characters or "an empty line", and "with control characters"), never the line, and the run id it expected.
- No bypass added: no flag carrying the id, no environment variable (brief). The gate is unchanged: no terminal, a failed read or another line still refuses before any credential is read.
- Scope note (deliberate): the discard is in the shared `tty`, so `bootstrap --fresh-account`'s prompts (FR-010 `ReadSecret`/`ReadLine`) also drop input typed before their prompt. Fail-safe: at worst the operator retypes. The boundary is the discard just ahead of the prompt: input arriving between the discard and the prompt (microseconds) is still read, as before.
- Dependency: **none added.** `golang.org/x/sys` is in `tools/go.mod` only as indirect and `tools/vendor/` holds only `golang.org/x/sys/execabs`; using `unix.IoctlSetInt` would vendor the whole `unix` package. The file already issues its `ioctl`s through `syscall` (`TCGETS`/`TCSETS`), which lacks `TCFLSH`, so `tty_flush_linux.go` defines it (`0x540B`) for the architectures of the generic Linux numbering, with a build constraint: elsewhere lz-live does not build rather than send another ioctl. Values checked 2026-10-19 (verified) in the module cache's `golang.org/x/sys@v0.5.0/unix/zerrors_linux_{amd64,arm64,386,arm,riscv64,s390x,loong64}.go` (`0x540b`), `mips64` `0x5407`, `ppc64le` `0x2000741f`.
- Files: `tools/cmd/lz-live/{tty_linux.go,tty_flush_linux.go,probe.go}`; tests `tools/cmd/lz-live/{tty_linux_test.go,probe_recovery_test.go,probe_check_test.go}`; `tasks.md` (task line added; ticked at close, after FINAL), `loop.md`, this file.

## Learnings

Class: guidance.
- A terminal prompt whose reader goroutine starts at construction reads type-ahead before any prompt exists; a flush alone cannot drop a line already held in user space. Read on demand, discard, then prompt. (T026)
- A pty test of "input before the prompt is ignored" waits until the slave has the bytes queued (`TIOCINQ` > 0) before the prompt, and types its answer only after the prompt is shown (watch the prompt stream), never on a fixed sleep. (T026)
