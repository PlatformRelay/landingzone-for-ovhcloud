## Design of the cases (from spec.md FR-006, FR-007, SC-005, data-model.md and the task text)

- **Fresh process** (`rcEntry`, dispatched in `init` before `TestMain`, as spec 003 T037's `swRun`): the test binary re-executed with `lz-live-entry <config>` runs `main`'s `run(args, deps)` with the probe world's host facts (checkout, HOME, fake git, the fake API's URL, `Terminal: openTTY` as production). Each process runs in its own session (`Setsid`); a kill is `SIGKILL` of its process group (its fake `tofu` with it).
- **Fake API** (`rcWorld.serve`, the probe world's `apiHook`): `GET /v1/me` and, for project `p1`, `GET …/alerting` (uuid[]), `GET …/alerting/{id}` (`cloud.alerting.Alerting`, threshold 1, delay 3600, the `/me` address) and `DELETE …/alerting/{id}`, shapes as T012's fake (kb `api/v1/cloud.json`, verified 2026-10-18 in T012). Alert A is in the project before every run. Every alert request is recorded.
- **Fake `tofu`** (`rcTofu`, the test binary behind `bin/tofu` while `bin/budget-tofu.mode` exists; everything else is `fakeTofu`): forward apply `lost` appends B to `remote-created` (the fake API reads it) and exits 1 with no state and no apply line; `create` also prints the `apply_complete` line for `module.project.ovh_cloud_project_alerting.this[0]` and writes state; `block` sleeps until killed. The apply of a destroy plan with state appends B to `remote-destroyed`. `output -json` prints `alert_id` (string), `budget_alert_check` (map with `alert_id`) and `run_id`, as T010 fixes the root's outputs.
- **Kill points** (deterministic, no timing): the first alert listing before any apply (the baseline listing, phase 3: `probe.env` and the passphrase written); the first forward apply (phase 4: both copies written); the first alert request after a failed apply (before the run's own end). Windows with no blocking point between two writes (after `probe.env` only; after the record copy only) are the disk of the next kill with the later write removed. Each killed start's disk is checked first (`windowDisk`: no state, no inventory entry, both copies exactly when killed at the apply). A blocked fake `tofu` runs in its own process group (the runner starts it so, `runner.go:151`) and exits when it is reparented. In the lost create's `exit` variant the run's own alert requests after the apply answer 403, so its sweep fails and it ends unreconciled (without that, a correct run sweeps B itself, review round 1). "No passphrase read" is approximated: the file is removed (row 1) or cut to an unusable value (rows 2, 3), so a cleanup that needs the passphrase fails; a read that ignores the value is not detected (narrowed in review round 1).
- **Observability**: tofu calls are counted in `tofu.log` (the root's calls; the pinned-version check `tofu version -json`, which every process runs before anything, goes to `tofu-version.log` and is not counted); "not refused" is a following start that exits 0 with no `unreconciled-run` in its output; "retired" is no `state/probes/<run-id>/` and no `state/baselines/<run-id>.json`; the fake API records every alert request, `404` on an absent id, `GET retired` for a listing made after the watched run directory was gone, and `destroyed <id>` when the fake `tofu`'s destroy removed an alert.

## Deviations and decision requests

- **DR-T013-a (lost baseline: deleted vs unreadable)**. The task's given is "both baseline copies deleted after a lost create (state absent, inventory absent)" → `--cleanup` refused as untrusted. FR-006 and data-model *Start-up phases and run classes* class a run with no state, no inventory entry and no baseline in either place as **pre-create**, and T011's `TestClassifyRun` row `no state, no inventory, no baseline → pre-create` fixes it; so with both copies deleted a correct implementation retires the run and the case could never pass. The test uses the untrusted run the predicate names instead: both copies present but unreadable (`{"run_id":`) → refused `BASELINE_INVALID`, nothing deleted; the `--accept-lost-baseline` rows are unchanged. **For the coordinator**: confirm, or amend FR-006 (e.g. a run whose record directory shows an apply attempt is never pre-create). Believed: the design's residual risk is a lost create whose two copies were both deleted by hand; it is then retired as pre-create and its alert stays until the owner sees it.
- **DR-T013-b (row 3 class)**. The task calls the "after the record copy" kill pre-create ("no passphrase read, no `tofu` call"); by data-model's predicate a valid record copy makes it baseline-backed, and only pre-create is said to need no passphrase. The row keeps its passphrase (review round 2) and asserts no `tofu` call, nothing deleted, retired, which data-model's "destroy if state" gives a stateless baseline-backed run. **For the coordinator**: confirm that a stateless baseline-backed cleanup calls no `tofu` (else T014 changes this row's `noTofu` through a TEST-class correction citing the answer).
- **Note (`--accept-lost-baseline` refusal code)**. Data-model fixes the refusal, not its exit code: the test asserts a non-zero exit that is not a usage error.

## Learnings

Class: guidance.
- A recovery case whose run "ends by itself" must make that run's own reconciliation fail (here: its alert requests after the apply refused), or a correct implementation reconciles in the first process and the case can never pass.
- A kill "between two writes" with no blocking point between them is the next blocking kill's disk with the later write removed; check that disk (`windowDisk`) before asserting on it, or an implementation that writes only one copy changes the row's class.
- The runner starts `tofu` in its own process group: killing the lz-live group leaves a blocked fake `tofu`; have it exit when reparented.
