## Design choices

- **`git` as pinned Wolfi packages, not a new base image.** `prepare.py` downloads `git-2.56.0-r0.apk` and its one missing library `libpcre2-8-0-10.49-r1.apk` from `packages.wolfi.dev/os/x86_64` by exact file name, checks each file's SHA-256, and unpacks the data segment over the exported `wolfi-base` root under the image's own projection rules plus: no member may pass through or land on a link, nothing existing is replaced (`xb`, `mkdir` on a non-directory fails, `symlink_to` on an existing path fails), control members other than `.PKGINFO`/`.melange.yaml`/`.SIGN.*` (install scripts) are refused. The apk database is not updated (apk is not used at run time).
- **Provenance, verified once and then pinned (2026-10-07, `~/.local/share/ovh-lz/review/t001-025/fetch-apks.py`):** `APKINDEX.tar.gz` (sha256 `a575a4a8…03df`) signature verified with `openssl dgst -sha256 -verify` against `etc/apk/keys/wolfi-signing.rsa.pub` from the pinned image's own rootfs → `Verified OK`; for each package the index checksum `C:` equals `Q1`+base64(SHA-1 of the control gzip stream) (git `Q1c/gXw3…Tw=`, pcre2 `Q1E4AUco…MQ=`), and the control's `datahash` equals the SHA-256 of the data stream. Wolfi packages carry no per-package signature (two gzip streams, not three): the trust chain is index signature → control checksum → data hash. Then the file SHA-256s were pinned (`33bc6d38…c10d`, `c2e8dacd…c38c`).
- **Dependency closure deliberately partial.** The resolver over the signed index (`resolve-git.py`) gives git's declared deps `so:libcurl.so.4 so:libexpat.so.1 so:libpcre2-8.so.0 so:libz.so.1`; libcurl pulls ~20 packages (krb5, ldap, sasl, nghttp…). ELF `NEEDED` (readelf, verified): `usr/bin/git` and `scalar` need only `libpcre2-8.so.0 libz.so.1 libc.so.6` (max `GLIBC_2.38`; the image has glibc 2.44, zlib present); only `git-http-fetch`, `git-http-push`, `git-remote-http` need libcurl (and expat). Those three are unpacked but cannot load: the runtime has no network, so no transport is wanted.
- **Pinned like the image.** `checks.Prepared` gains `Packages` (file name → SHA-256); `AdmitPins` requires the exact set (`maps.Equal`), so bundle admission (every run, and `lz-pack`) refuses a manifest whose packages differ. `verify:toolchain` (`VerifyRuntime`, every entry run) executes `/usr/bin/git --version` and requires `git version 2.56.0`; the qualified line gains `git=2.56.0`.
- **Boundary case.** `TestTrustedTargetsIgnoreCandidate` now runs each trusted target in two placements: hostile root `Taskfile.yml` (unchanged case) and a root `Taskfile.yml` that includes `stacks/Taskfile.yml` flattened, the latter defining the trusted target hostilely. In the `stacks` placement a candidate target `stacks-control` from the same file must first print its marker — proof the hostile file reaches the child, so the trusted verdict is not vacuous.
- **Revision name** `r4` (new resources; entry e1 of r4). Previous `r3-e2` stays published and installed.

## Learnings

Class: sensor, guidance.
- A deferred-link extractor must recheck every path for links at creation time, not only when the member is read: links of the same archive can chain out (round 1). Applies to any tar projection.
- A positive control in a negative test (`stacks-control` before the trusted verdict) turns "no effect" into a check that is red on the old entry, not vacuously green.
- Re-running the preparation from scratch and diffing manifests (0 removed / 0 changed) requalifies the old closure cheaply; keep `manifest-diff.py` for every runtime revision.
- ghcr publish: `gh auth token | oras login … --registry-config <tmp>` then `oras cp --from-oci-layout <layout>@<digest> <ref>:<tag> --to-registry-config <tmp>` (oras 1.3 `cp` takes `--to-registry-config`, not `--registry-config`).
- Proposal (owner): a follow-up task to bring `prepare.py`'s projection under a CI-run test (port to Go in `tools/internal/bundle`, or a host-side target).
