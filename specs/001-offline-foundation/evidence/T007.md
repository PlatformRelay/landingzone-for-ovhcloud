# T007 — Check registry, trace and DoD evaluator

Status: GREEN locally, 2026-10-04. Requirements: FR-004 (C004.1–C004.4), SC-003.
ADRs: 0008, 0019. Depends on T006.

## What exists

- `tools/internal/checks/traceability.go` implements the T006 contract: `ParseSpec`,
  `ParseTasks`, `ParseRegistry`/`DecodeStrict`, `CheckTrace` (15 rules), `Digest` and
  `EvaluateDoD`. The trace rules and DoD statuses are described in `T006.md`.
- `harness/checks.yaml` — the check registry. One entry per planned Task target in the
  `tasks.md` creator table (21 checks), each with its creating task, the requirements of its
  spec V row, its kind (`behavioral` or `docs`), its input scope and, where the spec asks for
  independent review, `review: true`. `requirements` records which ADRs are relevant to each
  FR/SC. That relevance is a reviewed judgement made for the registry, not copied from the
  tasks' own ADR lists, so `UNRELATED_ADR` is not circular. `task dod` and the `task check`
  aggregate are evaluators, not checks, and are not registered.
- `tools/cmd/lz-check` — `specs <spec-dir>` and `dod <path>`. `dod` reads
  `<root>/.local/evidence/checks/<check-id>.json` with the same strict decoder; malformed
  evidence exits 2 rather than being treated as missing.
- `Taskfile.yml` — `test:traceability`, `check:specs`, `dod`.
- `tools/cmd/lz-offline` (T003 entry), two changes needed to run these targets through it:
  1. `specs` and `docs` join the snapshot allowlist; the trace check reads them as data.
  2. One operator argument is admitted after a second `--`
     (`-- task dod -- modules/naming`). It must be a clean relative path (first character
     alphanumeric or `_`, then `[A-Za-z0-9._/-]`, at most 256 bytes, no `..` segment) and is
     refused for the trusted targets; it is passed to the inner Task after `--`.
  The installed entry was rebuilt with the recorded manifest digest
  (`2b9a1781…1330c`); `verify:toolchain` and `test:offline-boundary` re-qualified through it.

T007 also tightens T006's controls: a closed-task title suffix, prose with a slash and a date
after `Depends on` in the parse fixture; a repeated task field; a symlinked scope component;
a symlink inside a DoD scope; `.` as a DoD path; a rationale naming an unlisted ADR with the
same count as the list; a `../` registry scope. Each was added because a mutant survived or
would have survived without it.

## Limits

- **No evidence producer yet.** Nothing writes `.local/evidence/checks/*.json`, and the
  entry's snapshot excludes `.local`, so `task dod` through the entry reports every behavioural
  check `not-run` today. That is the honest status until a producer exists (T018/T022 decide
  whether the entry exports evidence or DoD runs on the host over admitted evidence). A
  self-written evidence file still has to match the current input digest and be internally
  consistent.
- **Registry fields.** The plan lists fixture provenance and evidence status as registry
  fields. Status is deliberately kept out (a status in the registry would be self-reported and
  could go stale); provenance is not yet recorded per check (the tofu streams' provenance is in
  `T004.md`). Add a field when a second fixture-consuming check exists.
- **One spec per registry.** Requirement ids are the spec's own (`FR-001`); a second spec with
  checks needs per-spec keys.
- **YAML form.** `harness/checks.yaml` is JSON-compatible YAML; block YAML and comments are
  refused, because the tools module has no YAML dependency and the sandbox cannot download one.
