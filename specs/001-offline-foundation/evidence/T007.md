# T007 — Check registry, trace and DoD evaluator

Status: GREEN locally, 2026-10-04. Requirements: FR-004 (C004.1–C004.4), SC-003.
ADRs: 0008, 0019. Depends on T006.

## What exists

- `tools/internal/checks/traceability.go` implements the T006 contract: `ParseSpec`,
  `ParseTasks`, `ParseRegistry`/`DecodeStrict`, `CheckTrace` (21 rules), `Digest`/`CheckDigest` and
  `EvaluateDoD`. The trace rules and DoD statuses are described in `T006.md`.
- `harness/checks.yaml` — the check registry. One entry per planned Task target in the
  `tasks.md` creator table (21 checks), each with its creating task, the requirements of its
  spec V row, its kind (`behavioral` or `docs`), its input scope and, where the spec asks for
  independent review, `review: true`. `requirements` records which ADRs are relevant to each
  FR/SC. That relevance is a reviewed judgement made for the registry, not copied from the
  tasks' own ADR lists, so `UNRELATED_ADR` is not circular. `task dod` and the `task check`
  aggregate are evaluators, not checks, and are not registered.
- `tools/cmd/lz-check` — `specs <spec-dir>` and `dod <path>`. `dod` reads
  `<root>/.local/evidence/checks/<check-id>.json` with the same strict decoder; malformed
  evidence exits 2 rather than being treated as missing.
- `Taskfile.yml` — `test:traceability`, `check:specs`, `dod`.
- `tools/cmd/lz-offline` (T003 entry), two changes needed to run these targets through it:
  1. `specs` and `docs` join the snapshot allowlist; the trace check reads them as data.
  2. One operator argument is admitted after a second `--`
     (`-- task dod -- modules/naming`). It must be a clean relative path (first character
     alphanumeric or `_`, then `[A-Za-z0-9._/-]`, at most 256 bytes, no `..` segment) and is
     refused for the trusted targets; it is passed to the inner Task after `--`.
  The installed entry was rebuilt with the recorded manifest digest
  (`2b9a1781…1330c`); `verify:toolchain` and `test:offline-boundary` re-qualified through it.

### After the first independent review

The first review found seven majors; each is fixed with a control written first and seen
failing:

- **Docs exemptions** — a `docs` check must be created by a docs-only task (trace
  `INVALID_EXEMPTION`), and DoD exempts it only while every file in its scope is Markdown;
  otherwise `fail INVALID_EXEMPTION`.
- **Task ↔ check link** — every `task <target>` inside a Verify command span must be a
  registered check or an evaluator (`UNKNOWN_CHECK`); every behavioural check's creator must
  run it in its Verify (`CHECK_NOT_VERIFIED`); a behavioural check's command must be
  `task <id>`; Evidence must name an evidence path (`MISSING_EVIDENCE`).
- **ADR coverage** — each task requirement needs at least one of its relevant ADRs
  (`MISSING_ADR`); a requirement registered with no ADRs counts as unregistered.
- **Evidence authenticity** — evidence carries a `producer`; only producers listed in the
  registry can yield `pass`, anything else is `review-required UNATTESTED_EVIDENCE`. The
  registry lists none, because nothing produces evidence yet, so no check can pass DoD until
  a producer is built and admitted.
- **Freshness** — the evidence digest covers the check's registry definition, its scope and
  its `inputs` (Taskfile, `tools/go.mod`, the checker itself). `test:traceability` now spans
  the whole `checks` package and `lz-check`.
- **Strict decoding** — keys must match field names exactly (case variants are unknown
  fields), required fields must be present, and nothing may be null; types and trailing data
  are left to `json.Unmarshal`, which rejects them.

### After the second independent review

The second review confirmed the first round's fixes and found three more majors and a minor:

- **Every task needs an applicable check** — a non-exempt task's Verify must run at least one
  registered check that shares one of its requirements, an evaluator, or a test command over
  one of its own paths (`NO_APPLICABLE_CHECK`); a registered check of other requirements is
  `UNRELATED_CHECK`. Tasks verified by an approved external procedure are listed in the
  registry's `procedures` with a reason (only T001); an entry for an unknown task is
  `UNKNOWN_PROCEDURE`.
- **Only real runs count** — a Verify command is read in a restricted grammar:
  `task <target> [-- args]` (optionally through the offline entry), `go [-C dir] test <pkgs>`
  with only `-run`, `-count`, `-v`, `-tags`, `-timeout`, and `[mise exec --] tofu -chdir=<dir> test`.
  `echo task x`, `task x --dry`, pipes, `task --list-all`, `go test -list`, an empty `-run`
  pattern and a flag missing its value do not count.
- **Paths of any extension** — a title token with a `/` or of the form `name.ext` is a path, so
  `tools/evil.js` in a docs-only task fails the exemption; this is tested through the parser,
  not on a hand-built task. Evidence must start with a backtick-quoted file path.
- **Compiled inputs (minor)** — checks built from the `checks` package hash the whole package.

### After the third independent review

Five more majors, each fixed behind a control seen failing first:

- **Evaluators** count only when a check they select (every check without an argument, else
  the checks whose scope covers the argument) shares one of the task's requirements:
  `task dod -- AGENTS.md` no longer verifies a forge task.
- **Paths** of `name.ext` form count whatever the extension's length (`main.c`,
  `build.gradle`).
- **Go packages** are exact: `go test ./internal/probes` covers files in that directory only;
  only `/...` selects a tree. `tofu -chdir=<dir> test` covers the module tree.
- **Shell grammar** — commands are split at unquoted `;`, `&&`, `||` with quote-aware
  tokenizing; quoted text is never a command, and a segment with any other shell syntax (pipe,
  background, redirection, substitution, globbing, escapes, an unbalanced quote, or `$`/`` ` ``
  inside double quotes) yields no command at all.
- **Flag values** — `-count` must be a positive integer; `-run` must be a non-empty pattern
  other than `^$`.

The fourth review found two gaps in the same fixes: a comment (`echo x # ; task y`) let later
segments through, and a directory path matched its parent package. A span with any
unsupported syntax now yields no command at all, and only a file lies in its parent package; a
directory must be selected itself. The 13 tokenizer and package-matching mutants were re-run
after this change (13/13 killed); the other guard sites were unchanged since the 133/133 run.

What the trace proves stays bounded: that each task names a real, applicable command in this
grammar. Whether it ran and passed is the DoD's question, answered only by admitted evidence.

T007 also tightens T006's controls: a closed-task title suffix, prose with a slash and a date
after `Depends on` in the parse fixture; a repeated task field; a symlinked scope component;
a symlink inside a DoD scope; `.` as a DoD path; a rationale naming an unlisted ADR with the
same count as the list; a `../` registry scope. Each was added because a mutant survived or
would have survived without it.

## Limits

- **No evidence producer yet.** Nothing writes `.local/evidence/checks/*.json`, the entry's
  snapshot excludes `.local`, and the registry admits no producer, so no behavioural check can
  pass DoD today: missing evidence is `not-run`, hand-written evidence is `review-required`.
  A producer name in a file is a label, not proof; the producer that T018/T022 build must
  write evidence where the candidate cannot (outside the snapshot) before it is admitted.
- **Registry fields.** The plan lists fixture provenance and evidence status as registry
  fields. Status is deliberately kept out (a status in the registry would be self-reported and
  could go stale); provenance is not yet recorded per check (the tofu streams' provenance is in
  `T004.md`). Add a field when a second fixture-consuming check exists.
- **One spec per registry.** Requirement ids are the spec's own (`FR-001`); a second spec with
  checks needs per-spec keys.
- **YAML form.** `harness/checks.yaml` is JSON-compatible YAML; block YAML and comments are
  refused, because the tools module has no YAML dependency and the sandbox cannot download one.
