## What `ci:foundation` does

- `lz-check ci-observe (<role> <candidate> <capture-dir>)...` (host, files only) turns GitHub's own output — `gh api …/actions/runs/<id>`, `…/runs/<id>/jobs`, the blob SHA of workflow and source at the run head (`gh api …/contents/<path>?ref=<head> --jq .sha`), `gh run view <id> --log` — plus `tree/`, a `git archive` of the run head, into one observation per run. It refuses a job of another run or attempt or head, a blob that is not a SHA, an empty log, a missing tree. The `check_digests` it records are `CheckDigest` (registry definition + scope + inputs, the same digest `dod` binds evidence with) of each source target in the run head's tree.
- `task ci:foundation` → `lz-check ci-runs` (offline, inside the entry) judges `pipelines/github/foundation-runs.json` against `pipelines/github/foundation-source.json` **and the judged tree**: at least one `head` and one `red-control` run; rejects `RUN_FOREIGN` (other repository, fork head, other workflow path, event other than push/pull_request), `RUN_STEPS` (step list other than the rendered one, e.g. an Action step), `RUN_STALE_HEAD` (candidate ≠ run head ≠ fetched `LZ_CANDIDATE_HEAD` ≠ `LZ_HEAD`; not a full SHA; **a head run whose target digests differ from the judged tree's**), `RUN_STALE_SOURCE` (workflow/source blob ≠ approved), `RUN_IDENTITY` (image/manifest/layer/entry/launcher/targets env ≠ source, extra or missing env, non-hosted runner, other runner image, token ≠ `Metadata: read`), `RUN_INCOMPLETE`, `RUN_CANCELLED`, `RUN_SKIPPED` (run, job or step), `RUN_FAILED`, `RUN_COUNT`, `RUN_ZERO_DISCOVERY`, `RUN_NOT_RED` (red control not failing with failed assertions — `--- FAIL:` lines — inside one listed target of the checks step after the earlier ones passed; a build/tool failure is not red enough), `RUN_DUPLICATE`, `RUN_ROLE`, `RUN_MISSING`, `RUNS_SYNTAX`; an absent record fails (`RUNS_MISSING`, exit 1).
- The workflow keeps deferring `ci:foundation` (it cannot judge its own run); `ci-source` enforces that only it may be deferred.

## Decision request

**Context.** `ci:foundation` binds a green run to the judged tree through the registry's `CheckDigest` of each foundation target. Round 2 verified that the registry under-declares what two kinds of check read: `test:dependencies` runs `lz-check deps` over the whole repository's HCL, but its scope is only its fixtures; every Go-based target reads `tools/vendor/**`, but inputs list only `tools/vendor/modules.txt`. A change there leaves both `ci:foundation` and `dod` evidence looking fresh.
**Options.** A (Recommended) — amend `harness/checks.yaml`: add `tools/vendor` to the inputs of every check that lists `tools/go.mod`, and add the repository HCL roots `test:dependencies` scans to its inputs (create the roots or teach `walkScope` that an absent input root is empty); a small follow-up task with its own tests. B — have `FoundationDigests` add a whole-tree digest of tracked files (needs git in the entry, or a gitignore-aware walk). C — accept the gap for maintainer-only development and record it in `decisions.md`.

## Learnings

- class `sensor`: binding CI run evidence to a tree needs a content digest of what decides each check, not only head SHAs inside the record; the repo's `CheckDigest` serves. Proposed: any future run-evidence judge reuses `FoundationDigests`.
- class `guidance`: a red control proves behaviour only if it shows failed assertions; check for `--- FAIL:` rather than any non-zero exit.
- class `spec`: the registry's scopes/inputs are now load-bearing for CI freshness, not only for `dod`; they under-declare repository HCL and vendored sources (Decision request).
- class `tooling`: the worktree guard refuses commands containing `github` in paths or `-run 'A|B'` regexes; put such invocations in a script under `~/.local/share/ovh-lz/review/`.
