## Task text (tasks.md)

T095 Keep a probe's companion reachable when its destroy fails, in tools/internal/live/runner.go,
test first in tools/internal/live/runner_test.go
- Requirements: FR-010, FR-011; ADRs: 0008. Depends on: T010.
- Verify: `task test:live-lane`: the companion's destroy plan and apply retry transient API
  failures (5xx, OAuth2 token errors) a bounded number of times with backoff inside the run
  deadline; when the companion's destroy still fails, the root is planned for destroy *without*
  the identities that own companion resources (or not destroyed at all), the run ends `fail`, and
  `--cleanup <run-id>` can bind the identity again and destroy the companion, then the root; a 4xx
  is never retried; mutants per clause. Rationale (coordinator 2026-10-10): T010 run
  20261010T173007Z-637a lost its tenant identity to a transient OAuth2 500 and left three
  resources no cleanup could reach.

## Decisions taken here

1. **Keep the root entirely** (the task's "or not destroyed at all"), not a partial destroy
   without the identities. Why: which root resources the companion depends on is not only the
   identity (OAuth2 client + its IAM policy): the companion's state lives in the root's
   `lzprobe-p1-<run-id>` bucket under the root's S3 user and credential, and P25 needs its own
   client and the tagged buckets. A partial destroy needs a per-root list of addresses to spare
   (`-exclude`, kept in step with the probe root by hand) and gains little: what it would remove
   is free or near-free and `--cleanup` removes it minutes later. Keeping the root needs no
   knowledge of the root, and the companion stays reachable by construction.
2. **The kept root is reported as a leftover**, not as expected: the leftover check is unchanged
   (no exemption for the kept root), so its probe resources appear in `leftovers.json` and the run
   fails on them too. They exist after the run and must go by `--cleanup`; an exemption would hide
   exactly what the owner has to act on. The run's error names the kept root and the cleanup command.
3. **Retry unit**: the whole companion destroy (`plan -destroy`, `show -json`, guard, `apply` of
   that file), because a saved plan cannot be applied again after a failed apply (stale).
   Attempts: 3 (backoff 20 s, then 60 s); a wait that would end after the destroy deadline is not
   started.
4. **Transient** = the failed call's stderr names a 5xx status, a transport error on the
   `…/oauth2/token` endpoint or `connection reset by peer`, **and no 4xx status**; a 4xx wins
   (never retried). A status counts only in a recognised context (review r1): after
   `status code`, after `oauth2: cannot fetch token: `, or before a standard HTTP reason phrase
   (any case) — a number in a response body (`400 Test Network`) is no status. A 429 is a 4xx and
   is not retried (task text; scope choice noted by the strong review leg). Error formats:
   `golang.org/x/oauth2` v0.37.0 `RetrieveError.Error()` (read 2026-10-10:
   `oauth2: cannot fetch token: <status>\nResponse: …`, or `oauth2: "<code>"` for an RFC 6749
   error, which is not retried); go-ovh's `OVHcloud API error (status code N): …` believed,
   UNVERIFIED (no local copy).
5. **`--cleanup`**: a companion that cannot be destroyed, or whose identity cannot be read or bound
   (API error, or a binding `*Refusal` — account.env edited since the run), keeps the root again,
   so a later cleanup can retry; only a refusal of the published values (reserved name, unpaired
   credential: `publishedRefusal`) still destroys the root, because the run refused the same values
   before the companion ran (review r1, the strong review leg: a `*Refusal` can arise at cleanup only).
6. **Run record add-on (T094 gap 1)**: every failed tofu call appends its stderr, and a failed
   apply its `diagnostic` events from the `-json` stream decoded to plain text (summary, address,
   detail = the API's answer), to `errors.txt` in the run record (0600), redacted with every secret
   the run knew at its end. Decoded, so a secret that JSON escapes (`<`, `"`, `\`) is redacted too
   (review r1); a stream line over 1 MiB is dropped, not buffered.
7. **Deadline margin** (strong-leg note, accepted): a wait is skipped only when it would end after the
   destroy deadline; it leaves no reserve for the next attempt or the root's destroy. With the
   45 min default and 80 s of backoff this is practically unreachable; recorded, not changed.

## Learnings

- class `guidance`: a cleanup-time decision that keys on an error *type* must ask which errors can
  arise only at cleanup (a binding `*Refusal` can, a published-value refusal cannot); wrap the
  deterministic ones in a type of their own instead of reusing `*Refusal` (review r1/r2).
- class `guidance`: classify HTTP statuses only in recognised contexts (`status code N`, the OAuth2
  `cannot fetch token: N`, a standard reason phrase); free text in a response body is not a status.
- class `guidance`: redact decoded text, not JSON: a secret JSON escapes (`<`, `"`, `\`) and literal
  redaction misses the escaped form.
- class `guidance`: editing `tests/live/probes/README.md` turns `docs:check` red until
  `docs/how-to/run-the-first-slice.md`'s blob and `last_verified` are updated after a re-check.
- class `sensor` (proposed task): capture the next live companion/API failure's `errors.txt` as a
  fixture and run `transient` over it (harness gap 1).
