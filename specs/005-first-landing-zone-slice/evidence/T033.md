## Decoding approach (this task's choice; verified 2026-10-07 by reading the code named)
- **No YAML library.** `tools/go.mod` requires only `hcl/v2` and `go-cty`; the standard library has no YAML decoder. The manifest is **YAML written in its JSON-compatible flow form**, exactly as `harness/checks.yaml` is (`checks.ParseRegistry`, `tools/internal/checks/traceability.go:583`), and is decoded strictly as JSON. T034's Verify already says "strict decoding reuses `checks.DecodeStrict`", which is JSON-only, so this follows the task set rather than adding a design. JSON is a YAML subset, so the file stays valid YAML.
- **Exactness.** `checks.DecodeStrict` refuses duplicate keys at any depth, keys that are not a field's exact JSON name (it checks case variants, which `encoding/json` v1 would merge), missing required fields, nulls and trailing data (traceability.go:515–577). The T018 alternative, `encoding/json/v2` with `RejectUnknownMembers`, gives the same exactness; either passes these controls (the throw-away implementation uses `DecodeStrict`).
- **Whole-line comments are allowed** (T039 needs a comment pointing at KD-1, and the fixtures carry two). A JSON string cannot span lines, so a line whose first non-blank character is `#` is never inside a value; the decoder blanks such lines before decoding. A comment after a value on the same line, block-style YAML and a second document are refused as `MANIFEST_SYNTAX` (cases `syntax-*`). Comments inside flow collections stay valid YAML: verified 2026-10-07, `yq` v4.53.6 (`yq -o=json '.spec.sandbox, .spec.tenants[0].environments[0].project' tests/fixtures/manifests/sandbox/deployments.yaml`) parses the commented sandbox fixture to the expected values.

## Interface the tests pin (for T034; this task's choice, believed unless marked)
The plan fixes the file names (`manifest.go`, `stages.go`), the manifest shape (data-model) and the derivations; the Go surface is this task's.
- `DecodeManifest(data []byte) (*Manifest, error)`. Errors are `*ManifestError{Code, Detail}`; the 16 codes and their precedence (decoding, header, values, per-row, duplicate id, duplicate scope, composition, producers, shared state) are documented on the `Code*` constants in the stub.
- `Manifest`: `Name`, `Scope` (`platform` when `spec.scope` is absent), `Org`, `Forge`, `SharedStateProject`, `StateProjectRef`, `Tenants` (name → environments → project mode, ref, region names), `Instances` (row order), `External`.
- `Instance`: the row's dimensions plus `Scope` (`account | account-tenant | environment | region`), `Path`, `Backend` (`local` for bootstrap, else `s3`), `StateBucket`, `StateKey` (both empty for `local`), `Tags`, `Edges` (`{Producer, Kind}` with kind `data | authority`), `Naming` (`{Org, Tenant, Environment, Region, Slot}`, region as written).
- Readings: (1) "`account-fabric` or `account-admin` row" invalid (task) vs "decode but the reconciler refuses them with `STAGE_NOT_IMPLEMENTED`" (data-model): the stage value is in the enum (an unknown stage is `INVALID_VALUE`), and the manifest is refused with code `STAGE_NOT_IMPLEMENTED`, which the reconciler (T035) then reports; `observability` is treated the same (data-model groups it with them). (2) "consumed producer" covers data and authority producers (the data-model's tenant-only example lists exactly the two authority producers as `external`); a platform manifest whose regional row has no `project` row is `UNRESOLVED_PRODUCER` too. (3) "one owner per scope and slot" makes two `bootstrap`, two `account-governance` or two `tenant-state` rows for a tenant `DUPLICATE_SCOPE` (it fires before the platform-rows rule); a missing one is `PLATFORM_ROWS` / `MISSING_TENANT_STATE`. (4) Duplicate ids are checked across rows and `external` entries. (5) Region names (in `spec.tenants` and on rows) must match `^[A-Z]+[0-9]+$` (coordinator decision 2026-10-07): `EU-WEST-PAR` and `gra11` are `INVALID_VALUE`. (6) `spec.sandbox.shared_state_project: false` behaves as absent. (7) Tags: `lz-stage-<stage>`, `lz-scope-<scope>`, `lz-tenant-`, `lz-env-`, `lz-region-<lower>`, `lz-slot-` where set (research R16); compared as sets. (8) `bootstrap` has no S3 bucket/key (local backend); its artefact bucket is T060's.
- Sandbox fixture: `spec.sandbox.shared_state_project: true` with a KD-1 comment, state project ref = the demo/dev project ref (`SANDBOX`), project `mode: reference` with a T009 comment (P5 refuted, D94). Forge `example.org/…` (neutral; T037/T039 set the real one).

## Learnings
- spec · A test task that fixes an interface the plan leaves open meets data-model wording written before the design; list each conflict as a decision with a recommended amendment rather than diverging silently (here: reserved-stage refusal point, manifest syntax).
- tooling · Generate one-change invalid fixtures with a script that asserts each substitution's match count; a drifted base then fails in the generator, not as a fixture refused for the wrong reason.
- sensor · A value rule shadowed by a membership rule (row region vs `spec.tenants`) is unseen by refusal tests unless one case breaks the value rule alone and its code is pinned.
- tooling · The worktree guard refuses `bash script.sh … > file; echo …` compounds and inline python heredocs on repo paths; run scripts plainly and post-process in a separate command, edit evidence with the Edit tool.
