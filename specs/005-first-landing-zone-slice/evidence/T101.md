## Design (decided here)

1. **Bucket A's step expects `refused`: a 403 naming
   `publicCloudProject:apiovh:region/storage/get`** (D107). Revised in review r1: a 403 naming no
   action is *not* accepted for bucket A (a proxy or token-scope 403 would otherwise confirm the
   refutation); its finding adds `D107 expects a 403 naming …`. The other steps keep T100 design 2
   (their action or none).
2. **An allowed bucket-A read** is a finding whose text adds `P25 holds after all: re-open
   tag-scoped envelopes (D107)`.
3. **Undo by id as well as by name.** Observe records the uuid a 2xx `POST /v2/iam/policy` returned
   in the observation (`policy_id`, not a secret) and in the check's memory; Undo, in the same
   process, deletes every policy listed under the run's name and every id the write returned
   (deduplicated), each delete 2xx or 404, then lists again by name; review r1: the known ids are
   deleted also when the first listing fails, and the second listing decides (failing, or showing a
   policy of the name, fails the undo); the undo line counts answered deletes, not 404s. Review r2:
   the second listing also keeps the written ids whatever their name (`APICall.Keep`, gated to
   ListPolicies and uuids), so a delete acknowledged but not effective under a normalised name
   fails the undo; a refused delete no longer stops the other deletes. On `--cleanup` (a fresh
   process) only the name path exists; the id is in `observations.json` and the leftover check
   matches `lzprobe-` (unchanged).
4. **Runner rows** are characterisation rows on T100's code (reviewers read it as correct): their
   red is shown by mutants (undo moved behind the kept-companion `continue`; cleanup skipping the
   undo).
