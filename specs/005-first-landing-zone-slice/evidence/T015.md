## Interface the tests pin (for T016; readings, believed unless marked)
The plan fixes neither the component's nor the stage's variables; these are this task's choice.
- `components/state-backend` inputs: `project_id`, `region` (e.g. `GRA`), `org`, `tenant` (null = account bucket), `instance`, `managed_in`, `s3_users` (`set(string)` of user keys, e.g. `platform`, `tenant`). Naming happens inside the component (a stage may not call `modules/naming`: `mayUse[stage] = [component]`, `tools/internal/checks/dependencies.go:216-224`, verified 2026-10-07).
- Component outputs: `bucket`, `region`, `project_id`, `endpoint` (`https://s3.<lower(region)>.io.cloud.ovh.net`; form from kb `install-controller.mdx:44` and the provider's `virtual_host` example, data-model manifest `state.endpoint`, verified 2026-10-07), `labels` (the bucket's tags), `s3_users` (`{<key> = {id, description, policy}}`, no credential), `s3_credentials` (sensitive, `{<key> = {access_key_id, secret_access_key}}`), `unlabelled` (addresses of each user's user, credential and policy, keyed by the user key).
- Names: bucket `naming(org, tenant, kind bucket, role state)` → `lz-bkt-state`, `lz-demo-bkt-state`; user description `naming(org, tenant, kind s3_user, role state-<key>)` → `lz-s3u-state-platform`, `lz-demo-s3u-state-tenant`.
- `stages/bootstrap` inputs: `org`, `state_project_id`, `state_region`, `instance`, `managed_in`; exactly one call `module "state_backend"` to `components/state-backend`; outputs exactly the data-model's `state_bucket`, `state_project_id`, `state_region`, `state_endpoint`, `platform_s3_user_id`, `unlabelled` (addresses from the stage root, `module.state_backend.…`) plus the sensitive `platform_s3 {access_key_id, secret_access_key}` (data-model *Sensitive outputs*).
- Policy (G6, every user): the union of `Resource` over the Allow statements is exactly `arn:aws:s3:::<this bucket>` and `…/*`; no NotResource/NotAction in an Allow; the backend's four actions each allowed on its resource in one unconditioned Allow (`s3:GetObject`/`PutObject`/`DeleteObject` on `<b>/*`, `s3:ListBucket` on `<b>`; review r1); every allowed action within T013's object/listing allowlist. **Deny (coordinator decision 2026-10-07)**: for each of `s3:DeleteObjectVersion`, `s3:PutBucketVersioning`, `s3:PutBucketPolicy`, `s3:DeleteBucketPolicy`, `s3:PutLifecycleConfiguration`, `s3:PutBucketCORS`, `s3:PutEncryptionConfiguration`, `s3:PutBucketAcl`, `s3:DeleteBucket`, a Deny statement without Condition, NotAction, NotResource, Principal or NotPrincipal (review r1) on `*` or on both `arn:aws:s3:::<bucket>` and `…/*`.
- `unlabelled` entries end in `<resource type>.<name>`, optionally with a `["<key>"]` index (review r1: T016 may key the resources or the module call). IAM action names from kb `s3-identity-and-access-management.mdx:263-317` (verified 2026-10-07): bucket deletes of lifecycle/CORS/encryption configuration are covered by the Put actions in AWS's action model (believed). `s3:DeleteObjectVersion`, `s3:PutBucketPolicy` and `s3:DeleteBucketPolicy` are **not** in OVHcloud's supported-action list: whether OVHcloud accepts or enforces a Deny on them is UNVERIFIED (harness gap 4).
- Where the Denies live is T016's choice (the dispatch: `modules/object-storage-user` or the component); the tests pin them at the component's outputs only.

## Observed tool behaviour (verified 2026-10-07)
- `mock_provider` `mock_resource … defaults` are the computed values at **plan** time in OpenTofu 1.13.0 (user id, access key id, secret compared equal in plan runs on the throw-away). `override_during = plan` is not an OpenTofu argument (1.10.3 and 1.13.0: `An argument named "override_during" is not expected here`).
- Host tofu is 1.10.3; the pinned 1.13.0 binary at `~/.local/share/ovh-lz/003-runtime-r3-e2/resources/tofu` runs on the host and is used by `~/.local/share/ovh-lz/review/t015-run.sh`.
- A test assertion may reference a child module call's outputs (`module.state_backend.labels`) of the configuration under test; it cannot reference a resource inside a child module. Hence the component exposes `labels` and `s3_users[*].policy` as outputs.
- An empty-map placeholder makes `output.s3_users["platform"]` an `Invalid index` error, not an assertion failure; the component stub therefore keys its placeholders by `var.s3_users`, and the stage's one policy assertion is wrapped in `try(…, false)` (the stage stub passes no users).
- `nonsensitive(<object>)` keeps the provider's nested sensitive mark on `secret_access_key`; an output of it without `sensitive = true` fails the plan with `Output refers to sensitive values` (mutant construction, iteration 2).

Proposal (T016 or coordinator): a `lz-check deps` rule that `components/state-backend` creates `ovh_cloud_project_storage` only through `modules/object-storage-protected` (no direct storage resource, no call to `modules/object-storage`) — same family as `RETAINED_UNPROTECTED`; until then, independent review of T016.

Covered by review and, from T038/T039, by `NAME_COLLISION`/stack plans; a cheap static sensor would be "a stage holds exactly one module call and no resource" (proposal).
3. The component's `labels`, `project_id` and `s3_users[*].policy` outputs are checked as outputs; that they equal the bucket's `tags`/`service_name` and the policy resource's `policy` is T016's to bind (recommended: module outputs read from the resource attributes, e.g. `modules/object-storage-protected` `tags`, `modules/object-storage-user` `policy`, each pinned by its module test).
4. OVHcloud's handling of a Deny on `s3:DeleteObjectVersion`, `s3:PutBucketPolicy`, `s3:DeleteBucketPolicy` (absent from the supported-action list) and whether a version delete is governed by `s3:DeleteObject` there is UNVERIFIED (T010 probes). If OVHcloud rejects a policy naming an unsupported action, T016's policy fails at apply: T010/T009 territory, not observable offline.
5. Object-level ACL writes (`s3:PutObjectAcl`), object lock and replication configuration are not in the decision's list and not pinned (proposal for the coordinator: add `s3:PutObjectAcl`, `s3:PutBucketObjectLockConfiguration`, `s3:PutReplicationConfiguration` to the Deny).

## Learnings
- tooling: OpenTofu `mock_resource` defaults are known at plan time (1.13.0), so plan-only tests of modules with `prevent_destroy` can still bind outputs to computed values (ids, credentials) through literal mock defaults; `override_during` does not exist in OpenTofu.
- tooling: the pinned 1.13.0 `tofu` from the runtime resources runs on the host; host 1.10.3 is too old for some test syntax — use the pinned binary in host helper scripts (`t015-run.sh`).
- guidance: a stub's placeholder outputs must have the shape the tests index (maps keyed by the given keys), or runs error instead of failing by assertion.
- guidance: an IAM policy test pins each needed action on its own resource in one statement (separate Action/Resource unions accept swapped pairs), and a Deny predicate refuses Condition, NotAction, NotResource, Principal and NotPrincipal (review r1).
- guidance: every input that reaches a resource gets a second value in some run (region, project), or a hard-coded argument passes (review r1).
- guidance: a credential-exposure check with literal mock values (`mock-secret-access-key`) can scan every other output by `strcontains`, which also catches the access key id.
