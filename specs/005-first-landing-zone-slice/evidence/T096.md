## Design (decided here)

1. **Where the helper runs: a post-apply step of lz-live's probe runner**, not a tofu `external`
   data source. An external program would get the credential through tofu (argv or a JSON stdin
   the provider logs at TRACE), run during plan/apply where the run core cannot order it before the
   destroy, and its writes would not be undone on a signal. As a runner step the credential goes
   from `tofu output -json` (stdout into memory) to the Go client and nowhere else: no file, no
   argv, no child environment; every secret value is added to the run's redactor first.
2. **Hook**: `live.ProbeCheck{Output, Public, Observe, Undo}` on `live.Probe.Check`; `lz-live`
   sets it for the `state-backend` root only (`state.Check`), so a missing output on that root is
   an error, not a silent skip. `live` cannot import the helper (the helper imports `live`), hence
   the injected hook.
3. **Undo is one point on every way out**: the destroy-on-exit calls `Undo` before it destroys the
   root — after a pass, a failed observation, a signal, the deadline, and on `--cleanup` (from the
   root's retained state). An `Undo` that fails keeps the root (like T095's kept stage) and names
   `--cleanup`: destroying the identities would leave the bucket's versions out of reach.
4. **A janitor identity in the probe root**: the state user cannot delete versions if its Deny
   holds, and the admin has no S3 key, so the root adds a second probe user
   (`lzprobe-state-janitor-<run-id>`) whose policy allows `s3:*` on the probe bucket only (an
   accepted pattern, fixture rule 2). Undo, with that credential: delete a bucket policy if one is
   set, re-enable versioning if it is not `Enabled`, delete every version and delete marker in the
   bucket, then list again and require it empty (P14 needs an empty bucket).
5. **Method gate widened only for the helper**: `S3Store` (bootstrap's store) keeps GET/PUT/HEAD.
   A separate `live.S3Checker` admits a closed set of nine named operations, each with its method
   and sub-resource fixed (`DELETE` only as `DeleteObject` on an object key, optionally with
   `versionId`, and `DeleteBucketPolicy` on `?policy`; never a bucket DELETE). It reuses the
   store's signer, endpoint rule, name checks, redirect refusal, size cap and quiet errors.
6. **Findings do not fail the run**: an answer other than the expected one (an accepted versioned
   DELETE, a refused backend action) is recorded with `as_expected: false`, listed under
   `findings` in `observations.json` and printed as `LZ-LIVE finding`; the run fails only when a
   step could not run (no answer, no version id) or the undo failed.

7. **Only the S3 error code of the server's text**: a code is kept when it has the shape of one
   (`^[A-Za-z][A-Za-z0-9.]{0,63}$`) and holds neither of the request's keys, else `unrecognised`;
   a listing body is parsed, never quoted; a version id is kept only as 1–1024 printable ASCII.
8. **Undo empties only a state-backend probe bucket**: the published bucket must match
   `^lzprobe-state-<run id, lowercased>$`, and Undo refuses more than 100 versions before deleting
   any (the check writes three).

## Learnings
- sensor: `encoding/xml` decodes any root element into a struct without `XMLName`: a parser of a
  server answer must check the root, or a 200 of another kind reads as an empty listing (r1).
- sensor: a helper that passes server-listed names (S3 keys) back into its own requests leaks them
  through the client's error text; wrap such errors with positions, and test with a listed name that
  carries a marker (r1).
- guidance: a "refusal of the published values" must include the check's own validation, not only the
  run core's parsing, or a refused output keeps a root forever (r1); and an output that a cleanup step
  needs must `depends_on` every resource that step's rights come from (r2).
- tooling: in a `tofu test` assertion `sort(keys(x)) == ["a"]` is always false (list vs tuple): use
  `tolist([...])`.
