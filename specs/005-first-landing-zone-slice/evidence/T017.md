## Interface the tests pin (for T018; believed, my reading of FR-005 and data-model)
- `BuildEnvelope(tofuOutput, Producer) (Envelope, error)`: drops `sensitive: true`; an entry with no
  `sensitive` marker is refused (`sensitive`), not assumed plain; a plain output whose name or any
  nested key matches the secret pattern is refused (`secret-key`); broken document → `malformed`.
- `ValidateEnvelope(fs.FS, []byte, Expectation) (Envelope, error)` reads `<stage>.schema.json` from the
  FS and requires `envelope.schema.json` there (repository schemas minus `<stage>.schema.json` →
  `unknown-stage`; minus `envelope.schema.json` → `envelope`, checked first), refuses with one
  `RefusalError` reason. `Expectation` carries instance id, stage and the project binding, no
  revision (r2: a revision field invited an unspecified staleness check).
- Reporting order where reasons could overlap: malformed → envelope header → producer → deny-list
  (secret-pattern key, null/`""`) → schema → KD-3 binding. Deny-list hits are reported as such even
  where the schema would also refuse.
- Malformed includes duplicate keys at any depth and trailing data (a lenient decoder lets the last
  duplicate win).
- `source_revision` must be a git object id (40 or 64 lower-case hex).
- Null/`""` refused anywhere in `values` (capabilities, optional `slot`, `budget_alert_id`); `[]` is
  valid (`pending_actions`, `unlabelled`).
- KD-3: for `stage = project`, `values.project_id` and `values.project_urn` must equal the
  expectation's `ProjectBinding`; no binding → refused (fail closed).
- One schema per stage plus `envelope.schema.json` under `schemas/outputs/` (plan *Project structure*).

## Scope decisions (for the coordinator)
- **Wrong producer and wrong account (KD-3)** are V012/T060–T061 (adapter) in tasks.md, but FR-005
  names both and the validator is where the adapter will call them, so the validator pins them
  here too; T060 still has to show the adapter passes the binding from `account.env`.
- **Stale artefact: not tested, by design.** ADR-0004 *Postponed until there is a need: the artefact
  transaction* (operator decision 2026-10-06) postpones generations and apply-time staleness checks;
  the envelope carries nothing a validator could judge staleness by (only `source_revision`, whose
  freshness is a run-level fact). FR-009's consumed-digest re-plan is T033/T037 territory. Adding a
  staleness rule here would be a design decision, not a test. Both review rounds' codex legs
  accepted the deferral; it still needs the coordinator's sign-off.
- **KD-3 covers `stage = project` only.** A `runtime` artefact's `scope.project_id` is not compared
  with the binding here; if wanted, it belongs to T060/T061 (adapter) or a decision.
- **Null/`""` refused anywhere in `values`** is stricter than data-model's "for capabilities"
  (FR-005: absent, never a placeholder). Proposal: say so in data-model *Output envelope* with T018.

## Learnings
Class: guidance.
- A deny-list control needs a member that only the primary mechanism catches (a sensitive output
  with a neutral name), or a pattern-only implementation passes.
- A binding check's negatives must be internally coherent (foreign id and matching URN), or a
  consistency-only check passes.
- Deny-list checks need a nested case at every entry point (builder and validator), not just one.
- Do not put a field into a pinned interface that no test exercises (`SourceRevision` in the
  expectation): it invites an unspecified check.
- A capture sidecar check binds the input digest too, so an edited root without a recapture fails.
