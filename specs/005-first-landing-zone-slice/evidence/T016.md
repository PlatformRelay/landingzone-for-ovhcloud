## Decisions taken here (coordinator items 1–5)
1. **Protection sensor (T015 gap 1, decision request 1 A).** New `lz-check deps` rule `STATE_BUCKET_UNPROTECTED` beside `RETAINED_UNPROTECTED` (`tools/internal/checks/dependencies.go`): in every library directory under `components/state-backend` (subdirectories and module-named hidden directories included; its `tests/` are test layer, outside) no bucket resource is declared (`ovh_cloud_project_storage`, `aws_s3_bucket`, `openstack_objectstorage_container_v1`), every module source is relative, and every directory reached transitively through local module calls that declares a bucket lies in `modules/object-storage-protected`. Data sources are not buckets. No allow-list, layer rule or baseline widened: the rule only adds findings; `mayUse` unchanged (`TestDependenciesLayerMatrixUnchanged` green); `DependencyRules` gains the rule (listed test updated, see *Test changes*).
2. **Where the Deny lives: the list in the component, the statement in `modules/object-storage-user`.** The module gets `deny_actions` (default `[]`, each `^s3:[A-Za-z]+$`, no null) and renders one `DenyGivenActions` statement (Deny, the given actions, `Resource = ["*"]`, nothing else) when non-empty; `components/state-backend` passes its nine actions as `local.deny_actions`. Why: (a) one resource owns the policy document — the component cannot add a statement without a second policy resource or recomputing the JSON; (b) the actions are the state backend's protection decision (versioned, retained bucket), not every S3 user's — a runtime bucket user (plan: `components/runtime/managed-only`) need not carry it; (c) three of the nine actions are UNVERIFIED on OVHcloud (gap 4): if T010 shows OVHcloud refuses a policy naming them, only the state-backend users fail and the fix is one list. T013/T014's module runs stay green unchanged (default adds no statement, pinned by `deny_actions_default_adds_no_statement`).
3. **Gap 3 closed for `labels`, `project_id`, `policy`.** Component `labels` = `module.bucket.tags` (protected module output `tags` = `ovh_cloud_project_storage.this.tags`), `project_id` = `module.bucket.project_id` (= `service_name`), `s3_users[*].policy` = `module.s3_user[*].policy` (= `ovh_cloud_project_user_s3_policy.this.policy`); each module output pinned by its module test against the resource attribute. `description` still comes from `modules/naming` (the user module has no description output; the tests compare it to the naming value).
4. **Probe root.** `tests/live/probes/state-backend/main.tf` adds the `DenyGivenActions` statement verbatim to the probe user's policy; `probe.tftest.hcl` run `policy_carries_the_state_backend_deny` compares the whole statement object; `tests/live/probes/README.md` row 7a (same command as row 7) says what T010 observes (acceptance, and the returned policy keeping every action) and what refutes it. Enforcement is not observed by that root (needs S3 calls with the credential).
5. **Not added:** `s3:PutObjectAcl`, object lock, replication (wait for T010).

## Learnings
- tooling: a reachability rule over `g.Uses` must skip directories of the scanned package itself, or a subdirectory finding is reported twice (once for itself, once from its caller).
- guidance: a mutant aimed at a consumer's test only kills if that test pins the clause; pick the target run from the test file, not from the call graph.
- sensor: a "only through module X" rule must close every way code reaches the package unscanned: direct resources (by type prefix, so configuration resources like lifecycle count), transitive local calls, and every non-relative source anywhere on the walk (external and own-repository `?ref=` alike) — both review rounds found one of these (T014 had the same pattern).
- guidance: order a credential after the policy that confines it (`depends_on`), so a refused policy stops the apply before a usable key exists.
