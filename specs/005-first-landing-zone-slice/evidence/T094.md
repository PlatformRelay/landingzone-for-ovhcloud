## Decisions taken here

1. **Allow loses `s3:GetObjectVersion`** (module and state-backend probe). It is the action the 400
   named; the OpenTofu S3 backend does not read old versions. Not replaced by a pattern: a `*` in an
   Allow widens (`s3:GetObjectVersion*` would also grant tagging/ACL reads of versions on AWS
   semantics) and the module's tests forbid wildcard Allow actions. Whether a GET with `versionId`
   is authorised as `s3:GetObject` on OVHcloud is UNVERIFIED; old state versions stay readable by
   the admin.
2. **Deny list (component, probe verbatim), eleven actions**:
   named, accepted — `s3:BypassGovernanceRetention`, `s3:PutBucketVersioning`,
   `s3:PutBucketObjectLockConfiguration`, `s3:PutLifecycleConfiguration`, `s3:PutBucketCORS`,
   `s3:PutEncryptionConfiguration`, `s3:PutBucketAcl`, `s3:DeleteBucket`;
   patterns, no named action exists — `s3:DeleteObjectVersion*`, `s3:PutBucketPolicy*`,
   `s3:DeleteBucketPolicy*`. New against T016's list: the two object-lock actions (dispatch intent
   "versioning/lifecycle/lock"; the bypass would let a locked version be deleted). Bucket policies are
   not implemented on OVHcloud yet (guide *Understanding the user policy evaluation process*: "subject
   to change with the upcoming implementation of bucket policies"); the two policy patterns keep the
   intent for when they are.
3. **`deny_actions` admits a trailing `*`** (`^s3:[A-Za-z]+\*?$`, at most 256 characters): needed for
   the patterns. A Deny only narrows; a bare `s3:*` and an inner `*`/`?` stay refused. The new risk —
   a pattern that denies what the backend needs (`s3:Delete*` would deny `s3:DeleteObject`, the lock
   file's delete) — is covered by a component assertion, not by the module.
4. **Assertions in a `tofu test` must refer to a configuration object**; the fixture/file reads are
   anchored on `output.bucket == "lz-bkt-state"` (tofu 1.13.0 refuses a condition with no reference:
   "must refer to at least one object").

## Pattern semantics — UNVERIFIED, what the re-run of T010 row 7 must observe

That OVHcloud *accepts* `s3:DeleteObjectVersion*`, `s3:PutBucketPolicy*`, `s3:DeleteBucketPolicy*`
follows from its own rule (the 400 answer). What a pattern *matches* when a request is evaluated is
UNVERIFIED: no OVHcloud source states prefix-glob semantics (the guide only shows `s3:*`), and
OVHcloud may not classify a versioned DELETE as `s3:DeleteObjectVersion` at all (it has no such named
action), in which case the version-delete Deny is inert and a versioned DELETE is authorised by the
Allow's `s3:DeleteObject`.

Row 7a (acceptance; the probe as committed here):
1. `POST /cloud/project/<p>/user/<u>/policy` succeeds (no 400); if refused, keep the whole body and
   compare it with the fixture.
2. `GET /cloud/project/<p>/user/<u>/policy` returns the Allow statement with its six actions and
   `DenyGivenActions` with the eleven actions above, each verbatim (patterns neither dropped nor
   expanded), `Resource = ["*"]`.

Enforcement (not row 7a: needs S3 calls with the probe user's credential, the probe's second stage,
P1–P3), with that credential on the probe bucket:
3. PutObject, GetObject and DeleteObject (no `versionId`) of a `*.tflock` key succeed: no pattern
   catches the backend's actions.
4. `DeleteObject` with a `versionId` of an older version is refused (403). If it succeeds, the
   `s3:DeleteObjectVersion*` Deny is inert on OVHcloud and version protection needs another control
   (decision for the owner, ADR-0009).
5. `PutBucketVersioning` (Suspended) and `PutBucketObjectLockConfiguration` are refused (named Deny).
6. A `PutBucketPolicy` call: refused or not implemented; record which.

## Learnings

- class `guidance`: `tofu test` refuses an assert whose condition references no configuration object;
  anchor file/fixture reads on an output.
- class `guidance`: a change to a module a pinned stage plan reads (any non-test `.tf`, even a
  comment) needs `capture-stage-plan.sh` for each such stage before `test:outputs` is green.
- class `sensor`: a fixture-count check does not pin content; pin a digest too.
- class `tooling` (proposed task): the live lane should keep the body of a refused API call in the
  run record, so OVHcloud refusals can be captured as fixtures instead of transcribed.
- class `spec` (proposed task): `deny_actions` validates against OVHcloud's accepted-action rule
  (gap 4).
