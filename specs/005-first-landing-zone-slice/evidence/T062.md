## Learnings
- sensor: a new row of an untested path (`chain -- <instance>`) run through a harness judge surfaced a pre-existing defect (state reads without their run locks); run new entry paths through the judging harness, not a bespoke one (Iterations 2).
- sensor: a completeness rule needs a two-instance row for every per-instance subject; one tenant hid the collapse of every tenant's binding into one subject (r1 codex).
- guidance: a cleanup for a write that may have happened is registered before the request, keyed by something the caller chose (a name), not by what the answer returns (r1/r2 IAM policy).
- guidance: "create a lock object" means a conditional create (If-None-Match), never check-then-put (r1 codex).
- tooling: exec copies distinct Stdout/Stderr writers in separate goroutines; capture both through one writer (r1 codex).
- spec (proposed to the owner): decide whether chains on different tenants may run side by side (they no longer can: reading 6) and, if so, how the leftover check reads retained states.
