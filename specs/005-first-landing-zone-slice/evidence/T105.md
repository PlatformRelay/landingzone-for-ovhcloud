## Choices

1. **Tag values (deviation from the task's literal "same values", recorded for the owner).** The keys are the project stage's keys (`lz:managed-by`, `lz:managed-in`, `lz:instance`, `lz:release`, `lz:tenant`); `lz:managed-by`, `lz:release` and `lz:tenant` keep their values. `lz:managed-in` and `lz:instance` now name `account-governance` (`…//stacks/account/account-governance`, `account-governance`) instead of the project stack (`…//stacks/tenants/demo/dev/project`, `demo-dev-project`). Reasons (verified 2026-10-13 by reading the code named): (a) data-model *Label set* defines both as the generated path and instance id of the stack that sets the labels, and the tags now live in `account-governance`'s state; (b) reproducing the project stack's values needs a new per-tenant input that `account-governance` does not have: the stage table gives it no data edge to `project` (the order is the reverse, `project` has an authority edge on it, `tools/internal/stacks/stages.go:27-31`), so the values would have to be generated by Terramate from the manifest rows (`stacks/_lz/main.tm.hcl`, `globals.tm.hcl`) or added to the adapter's resolved input (`tools/internal/stacks/adapter.go:264-276`) — both outside this task's named files; (c) a tenant with two environments (the `growth` fixture, `tests/fixtures/manifests/growth/deployments.yaml:67-70`) has two project stacks and so two different value pairs, while the stage takes one project per tenant. The L7 `project-tags` assertion (`tools/internal/live/observe.go:641-657`) checks `lz:managed-by = opentofu`, that `lz:managed-in`, `lz:instance`, `lz:release` are set, and `lz:tenant` = the row's tenant: it holds for both choices. If the owner wants the project stack's values, the follow-up is a per-environment input to `account-governance` (generator or adapter change), filed as a task.
2. **Module boundary.** A new layer-1 module `modules/iam-resource-tags` (one resource, `urn` and `tags` in, both read back out), called by the component; no component in the repository declares a resource directly (verified: `grep -rln '^resource' components/` is empty), and `account-governance` may call only `components/identity/ovh-native` (STAGE_COMPONENT_CALLS). `task test:dependencies` classifies it without a rule change (`DEPENDENCIES_OK dirs=37`, was 36). It is not a retained package: destroying it removes only its keys (provider docs `iam_resource_tags`, Notes; kb mirror read 2026-10-13).
3. **Label call.** The component calls `modules/naming` per tenant with kind `project`, role `main` (the call `components/project-factory` makes), tenant = the map key, and its own `org`, `instance`, `managed_in`. No new input to the component or the stage.
4. **project-factory keeps its `labels` output.** The `project` stage keeps receiving `org`, `instance`, `managed_in` (the generator passes them to every stage, pinned by `TestGenerateStackInvariants`, `tools/internal/stacks/generate_test.go:803-807`); with the label call removed they would be unused and TFLint's `terraform_unused_declarations` (recommended preset, `.tflint.hcl`) would fail the stage. So `components/project-factory` keeps the `modules/naming` call and publishes the scope's label set as `labels` (description says no resource carries it), and only the `tags` wiring into `modules/cloud-project` is removed. Dropping those inputs from the project stage is a generator change outside this task.
5. **Live state (verified 2026-10-13, read evidence/T049.md runs 1 and 3).** `account-governance` is applied and retained with five resources at the eight-address layout's `demo` addresses; T105 keeps every one of those addresses and adds only `module.project_tags["<t>"].ovh_iam_resource_tags.this`. `TestOutputsAccountGovernanceStagePlan` pins the exact address set (old set plus the tag addresses). The platform policy's `allow` change is an in-place update (T049 run 2 planned exactly that for the T103 change). `demo-dev-project` holds nothing (runs 1 and 3 failed at its first apply), so dropping its tag resource destroys nothing.
6. **T103/T104 pins.** The component's T104 `iam/resource/get` assert is replaced by a broader one: no `account:` action of any case in the platform policy. The Go G5 filter refuses every `account:` action on every policy again (the pre-T103 form). The exact-set pins go back to `["publicCloudProject:apiovh:*"]`.
7. **L7 `project-tags`** (`tools/internal/live/observe.go:881-910`) reads `GET /iam/resource/{urn}` with the admin's bearer and checks the keys in Choice 1: unchanged code, `go test ./internal/live` green.
8. **Docs.** research R6 (who tags and why, the three T049 refusals), R7 fallback line, R12 (`ovh_iam_resource_tags` row: owned by `account-governance`), data-model *Label set* note, how-to status and *What is still unverified*. ## Learnings

- spec: a task that moves a resource between stacks and asks for "the same values" should say which values: labels that name the managing stack (`lz:managed-in`, `lz:instance`) change with the move unless a new input carries the old stack's identity.
- tooling: a capture mutant must also neutralise the stage's own `tofu test` pin, because the capture runs the stage's tests and fails before the Go pin is reached.
- guidance: TFLint's `terraform_unused_declarations` plus the generator's uniform stage inputs means a component cannot drop a naming call without a generator change; check the stage's inputs before removing the last consumer of one.
