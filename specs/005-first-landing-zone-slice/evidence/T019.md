## Interface the tests pin (for T020; readings, believed unless marked)
The plan fixes the resource types (T020 Verify), not the variables or outputs; these are this task's choice.
- `modules/iam-service-account`: inputs `name` (naming output, kind `service_account`), `description`; resource `ovh_me_api_oauth2_client.this` with `flow = "CLIENT_CREDENTIALS"` fixed (not an input) and no `callback_urls`; outputs `client_id`, `identity` (both plain), `client_secret` (sensitive).
- `modules/iam-policy`: inputs `name`, `description`, `identities`, `resources`, `allow` (`set(string)` each), `conditions` (optional object tree, default null: `operator`, optional `values` map, optional `condition` list to three levels — the 2.21.0 schema's depth); resource `ovh_iam_policy.this`; outputs `id`, `name`. The module sets no `deny`, `except`, `permissions_groups` (nor `expired_at`).
- `modules/identity-group`: inputs `name`, `description`, `role` (default `NONE`, not nullable, one of `ADMIN`/`REGULAR`/`UNPRIVILEGED`/`NONE`, case-sensitive); resource `ovh_me_identity_group.this`; outputs `urn`, `name`.
- Readings: (1) "policy passes … unchanged" = each of `identities`, `resources`, `allow` equals the given set exactly (nothing added, nothing dropped) and the condition tree arrives whole at every level; the module adds no scope of its own: no `permissions_groups` (it grants its own actions, `iam_policy.md:93`), no `except`/`deny` (`iam_policy.md:91-92`). Whether an action list is acceptable (tenant allowlist, no IAM action, guard G5) is the caller's check (T023/T024), so the module passes a wildcard such as `publicCloudProject:apiovh:*` (platform deployer, R6) unchanged. (2) "Pair actions with resources" (T015 lesson): `ovh_iam_policy` grants every `allow` action on every `resources` URN in one statement, so a pair cannot be swapped inside one policy; each run asserts `allow` and `resources` together for one fixture, and two fixtures (tenant: 13 P9 actions on one project URN; platform: one wildcard action on two URNs, two identities) carry every guard, so a fixture-conditioned implementation fails one of them. (3) "secret only as sensitive output" = `client_secret` output sensitive, equal to the resource's secret, and the secret's literal mock value in neither `client_id` nor `identity` (T015 lesson: `strcontains` over every other output). (4) "`identity` URN exported" = output equal to the resource's `identity`, plain (it is published to policies); `client_id` exported plain too (credential file, R6). (5) "role defaults to `NONE`": no role → `NONE`; a given valid role passes; a null role → `NONE` (the schema's `role` is optional, not computed: a null would leave the role to the API, UNVERIFIED default); unknown or lower-case roles refused.
- Schema: attribute names from the pinned ovh 2.21.0 provider schema dumped offline (`~/.local/share/ovh-lz/review/t013-schema.py` over T008's `schema.json`, verified 2026-10-07): client `name`, `description`, `flow` (required), `callback_urls` (optional), `client_id`, `identity` (computed), `client_secret` (computed, sensitive), no `discard_client_secret` (P20); policy `name`, `identities`, `resources` (required), `description`, `allow`, `deny`, `except`, `permissions_groups`, `expired_at` (optional), `conditions` block (max 1) with `condition` blocks to three levels; group `name` (required), `description`, `role` (optional), `urn` (computed).
- OVH sources (kb mirror, read 2026-10-07): `CLIENT_CREDENTIALS` needs no callback URL (`manage-and-operate/api/manage-service-account.mdx:130-135`); OAuth2 identity URN form `urn:v1:<eu|ca>:identity:credential:<nic>/oauth2-<clientId>` (same guide :154); group URN form `urn:v1:eu:identity:group:<nic>/<name>` (`account-information/iam-policies-api.mdx:437`); group roles `ADMIN, REGULAR, UNPRIVILEGED, NONE` (`me_identity_group.md:23`, `api/v1/me.json` enum); conditions to three levels, `MATCH` terminal (`iam_policy.md:97-109`). The P9 action names: all thirteen present in `kb/api/v1/cloud.json` (grep, 2026-10-07). What each group role grants, P8 (identity usable in a policy) and condition evaluation (P25) are UNVERIFIED live.

## Learnings
- tooling: the mocked provider still runs the schema's enum validators (`flow`, `role`): a stub placeholder must be a valid but wrong value, and a module-level enum validation mutant is caught by the provider instead (equivalent in effect).
- tooling: in a `tofu test` assertion `var.<x>` is the run's raw value (a tuple for a list literal), so compare with `toset(var.<x>)` against a set attribute.
- guidance: mock defaults for ids must differ from every other value the tests compare (`client_id`, `name`), or an id-swap mutant is unrealisable and the evidence over-claims (review r1).
- guidance: a "passes unchanged" test pins the full scope and ceiling in every run that varies an input (here the condition runs), not only in the fixture runs, or a fixture-conditioned implementation escapes (review r1; T013 lesson extended).
