## Choices

1. **Action names** (verified 2026-10-13, `kb/api/v2/iam.json`): `PUT /iam/resource/{resourceURN}` requires `account:apiovh:iam/resource/edit`, which is the action named in T049 run 1's 403 for `ovh_iam_resource_tags`. The schema lists **no** IAM action for `GET /iam/resource/{resourceURN}` (`iamActions` absent), and `account:apiovh:iam/resource/get` appears nowhere in kb. It is added because D108 and the task name it; whether OVHcloud knows the action, ignores it, or refuses a policy holding it is UNVERIFIED until the T049 re-run (the `account-governance` update in place is the first place a refusal would show). Corrected after review (strong review leg r1, verified 2026-10-13 against `kb/api/v2/iam.json:916`): the PUT's `longDescription` says adding or removing tags through it also requires `$resourceType:apiovh:iam/resource/tag/add` / `tag/remove`, here `publicCloudProject:apiovh:iam/resource/tag/{add,remove}`; `publicCloudProject:apiovh:*` covers both, so nothing is added, and main.tf and research R6 now say a narrower platform list must name them. If the T049 re-run is refused again (e.g. OVHcloud evaluates `account:` actions only on the account URN), the next step is an operator decision; the grant is not widened to the account URN (research R6, how-to).
2. **Resources**: unchanged, `[for t in var.tenants : t.project_urn]` — never the account URN or `*`. The `modules/iam-policy` `allow` input is a `set(string)` applied to every resource for every identity (verified, read `modules/iam-policy/variables.tf`, `main.tf`), so one list is enough.
3. **Fake API credentials** (`tools/internal/live/testdata/api/credentials.json`, `platform-deployer`): a fake action list, documented there as not derived from R6; no fake route checks `iam/resource` actions for it (verified, `git grep` 2026-10-13). Unchanged.
4. **Deployer-binding assertion** (`tools/internal/live/observe.go:940`): checks `GET /auth/details`, not the policy's actions. Unchanged. No leftover exemption, synthetic world (`tests/fixtures/ovhcloud/synthetic/*`: those policies are `lz-sandbox-admin`'s) or bootstrap admin list pins the platform policy (verified, `git grep 'publicCloudProject:apiovh:\*'` 2026-10-13).
5. **Plan-level G5 filter widened, narrowly** (`tools/internal/stacks/outputs_stage_test.go`, `TestOutputsAccountGovernanceStagePlan`): it refused any `account:` action on every planned policy, the platform one included, so the re-captured plan failed it with "action \"account:apiovh:iam/resource/edit\" is outside every deployer grant (G5)". contracts/checks.md names G5 *tenant policy scope*; the platform grant is the task's own claim (D108). The filter now admits exactly the two named actions, on the platform policy's address only; any other `account:` action, on any policy, still fails, and the exact platform action list is pinned separately (`wantAllow`). This is the allow-list change the task orders, not one made to get green; flagged here for the reviewer.
6. **Generated stacks**: `task stacks:generate` (pinned Terramate 0.17.3) leaves the tree unchanged — no generated file carries the policy.
