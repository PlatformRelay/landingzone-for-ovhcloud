## Key convention the tests pin (for T002)

Interpretation of R18 ("`requirements` keyed `005/FR-001`, the spec dir selecting the prefix") and T002 ("spec 001 keys keep working"), verified against the files 2026-10-06:

- `Trace.Spec` = leading digits of the spec directory name (`specs/005-y` → `005`).
- Every registry key that belongs to a spec carries its prefix: `requirements` keys, check `requirements` entries, check `creator`, `procedures` keys (`005/FR-001`, `005/T001`). Unprefixed keys are spec 001's, so the real `harness/checks.yaml` needs no migration. Tasks keep naming requirements unprefixed (`Requirements: FR-014`), as spec 005's tasks.md does.
- A check may list requirements of several specs (needed in practice: spec 005 T006 verifies with spec 001's `task test:dependencies`); its creator check runs only in the creator's spec trace.
- Checks, requirements, creators and procedures of another spec are neither findings nor coverage.
- `ParseSpec` must also read spec 005's heading form `- **FR-001 Naming** — …` (believed defect found while framing: the current regex `^- \*\*((?:FR|SC)-\d{3})\*\*:` reads only `SC-001`–`SC-005` from spec 005, so `check:specs` on spec 005 would silently drop all 14 FRs). Pinned by `TestTraceabilityParseNamedRequirements`; implemented in T002 (traceability.go is in T002's file list).
