## Design (decided here)

1. **Module**: `modules/object-storage-protected` serves state buckets only (its one caller is
   `components/state-backend`), so it always enables Object Lock with a default **governance**
   rule; mode is not an input. New required input `retention_days` → `period = "P<n>D"`.
2. **Component**: input `state_retention_days`, default **7** (short: a week of state history
   protected against a leaked state credential; the account's governance bypass empties it). Bounds:
   whole number, **1 ≤ n ≤ 365**; minimum from the guide (`s3-managing-object-lock.mdx:51`), maximum
   decided here (the guide sets none; a longer retention is an owner decision, since every state
   version is kept that long). Same validation in the module (defence in depth, one message each).
   No stage passes it (default).
3. **State user**: Deny list unchanged; `s3:BypassGovernanceRetention` stays in it (a named action,
   whose Deny T010 row 11 showed enforced for its sibling `s3:PutBucketVersioning`).
4. **Probe root**: the probe bucket gets the same lock with `P1D` (the guide's minimum); the
   janitor's policy names `s3:BypassGovernanceRetention` beside `s3:*` (the bypass is documented for
   that named permission; what `*` matches is UNVERIFIED, T094).
5. **S3 checker**: `S3Call.Bypass` sends a signed `x-amz-bypass-governance-retention: true`, admitted
   only on a `DeleteObject` with a `versionId`.
6. **Check** (now ten steps): after the seven of T096, `delete-older-version-bypass` (state user,
   older version, bypass header: refused AccessDenied — the Deny / missing grant on the bypass),
   placed right after `delete-older-version`; then `janitor-delete-locked` (janitor, the newer
   (second PUT's) version, no bypass: refused AccessDenied — retention holds even for `s3:*`) and
   `janitor-delete-bypass` (janitor, the newer version, bypass: allowed 2xx). Undo sends the bypass
   on every versioned DELETE. Destroy success is the run's own result (destroy-on-exit + leftover
   check), not an observation. Review r1: a step whose version an earlier allowed versioned DELETE
   of the run removed is recorded `skipped` (no request, no finding, no error): the earlier step's
   finding already says the lock was not in force.

## Learnings
- guidance: when observation steps share a resource, a later step must not read the effect of an
  earlier allowed step as its own answer: track what the run already removed and record a dependent
  step `skipped`, not a finding (r1).
- sensor: a protection layered over an earlier one (lock over Deny) hides the earlier one from the
  same probe; say in the evidence which signal is lost and carry it as a counterpoint (r2).
- tooling: `tofu test` asserts on a child module's output (`module.bucket.object_lock`), so a
  component can pin what it passes to a module without a new root output (contradicts the T015 gap
  note "not observable here").
- tooling: a round-2 brief edit that fails leaves the round-1 brief in place; check the brief before
  starting the legs.
