## Design

1. `extractReleaseTools` (`prepare.go:585-619`) walks one table, `releaseTools`: tofu, terramate and task as the one bounded regular member of the tool's name in a gzipped tar (`tarMember`), tflint as the only file of a zip (`zipOnlyMember`). Each is read by `readVerified` against `checks.Artifacts[name]`, so what is unpacked is the very bytes that matched the pin, and written `0o700` with `O_EXCL` (`writeNew`). `copyToolchain` is gone; `prepareStage` calls `copyGo` directly. `zipOnlyMember` takes an `int64` bound like `tarMember`, so both fit one table.
2. Bounds: `maxTofuBytes` and `maxTerramateBytes` are 256 MiB. The real members are 114,188,448 B (tofu 1.13.0) and 101,060,729 B (terramate 0.17.3); the archives are 35 MB and 80 MB, under `maxInputBytes` (256 MiB) (verified 2026-10-18, `tar -tvzf` on `~/.local/share/ovh-lz/001-toolchain/inputs/`).
3. Member names: both real archives hold their binary as a bare top-level name (`tofu`; `terramate` beside `terramate-ls` and `cosign.pub`), regular, `0755`, which `tarMember`'s exact-name rule accepts (verified 2026-10-18, `tar -tvzf`). `terramate-ls` is not taken, as before (the toolchain copy took `terramate` only).
4. Bundle content on the real inputs is unchanged: each archive's member hashes to the toolchain binary r4-e2 was prepared from (verified 2026-10-18, host, read-only):

```
$ sha256sum tofu_1.13.0_linux_amd64.tar.gz terramate_0.17.3_linux_x86_64.tar.gz ../tools/tofu/tofu ../tools/terramate/terramate

$ tar -xzOf terramate_0.17.3_linux_x86_64.tar.gz terramate | sha256sum

```

5. Consequence: `Prepare` no longer reads `<toolchain>/tools/{tofu,terramate}`; the `-toolchain` root supplies the Go tree only. The pins are unchanged, so `resources.json` and `AdmitPins` are unaffected.

## Learnings

Class: guidance. When a fix moves a binary from a copied source to a verified archive, check the real archive's member names and sizes against the extractor's exact-name rule and bound before writing it, and hash the real member against the old source, so the bundle's content is shown unchanged; a refusal row whose input the earlier verification already refuses does not reach the new code: pair it with a re-pinned row that does.
