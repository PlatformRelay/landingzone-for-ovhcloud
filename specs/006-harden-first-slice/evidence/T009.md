## Task text (tasks.md)

T009 [US1] Write scratch-home tests in tools/internal/live/env_test.go and tools/internal/live/bootstrap_state_test.go. Requirements: FR-007; ADRs: 0009, 0021. Depends on: T004. Cases (given / when / then → defect exposed): (1) given a sentinel `HOME` in the test process / when `Command` builds a child with an explicit home / then the child's `HOME` is that home → exposes `os.Getenv("HOME")` in `env.go:26-29`. (2) given the sentinel / when the bootstrap phases `state`, `publish` and `verify` start their children / then none sees the sentinel → exposes an unpinned bootstrap path. (3) given the sentinel / when probe, plan, apply, destroy and chain start children / then none sees it → exposes a regression on paths fixed today. Verify: `task test:bootstrap; task test:live-lane`: the first case fails against the stub of the new `Command` signature; the other two are pins of behaviour that holds today.

## What the tests pin (for T015)

- The sentinel is a fresh directory set as the test process's `HOME` after the harness is built (the harnesses set their own fake `HOME`; the sentinel replaces it). A child "sees" it when its `HOME` is empty, or any variable's value contains the sentinel path (so a `TF_DATA_DIR` or other path under the caller's home is caught too, not only `HOME`). Helper: `childHomeNotCallers`.
- Case 1, `TestEnvCommandTakesHome`: runs the real child (the test binary's `fakeChildArg` mode, which writes its environment) and requires `HOME=<the home handed>` and no sentinel anywhere.
- Case 2, `TestBootstrapStateChildHome`: T056's harness on the current sandbox; state, publish and verify must pass (ran or unchanged), every fake tofu call of the run is judged, and children must have run in both the `bootstrap` root (state) and the `account-governance` root (verify). Publish starts no child today (`stateRun.publish`, `bootstrap_state.go:522-547`, read 2026-10-15); any child it starts later is judged by the same loop.
- Case 3, `TestEnvChildHomeEveryPath`: `probe` (the `Runner`, which `lz-live probe` builds, `cmd/lz-live/probe.go:217`), `plan` (a steady account with the two credential producers touched, as `TestApplyPlanOnly`'s exit-0 row; a fresh account blocks plan with exit 2), `apply` (`all`, the five stacks in order), `destroy` (`destroy -- demo-dev-gra11-runtime` on a steady account), `chain` (the whole chain, its destroy-on-exit included). Each requires success (probe: `Execute` returns nil; the lane verbs: exit 0) and that the verb did its work (probe: an `init`, `plan`, `apply` and `destroy` call on its stack; plan: the planned set; apply: the applied set; destroy and chain: the destroyed set), so a run that stops before its children cannot pass vacuously (review round 1).

## Learnings

Class: guidance.
- A pin over a harness run must check the run succeeded and that the verb did its work; copying a neighbour test that discards the run's error (`_, _ = execute(...)`) imports its vacuity.
- A "nothing of the caller's reaches the child" check should search every variable's value for the sentinel, not only `HOME`: a data directory under the caller's home is the same leak (the `bootstrap-datadir-under-caller` control).
- `plan -- all` on a fresh lane harness is blocked (exit 2) by design; a plan pin needs `steady` plus touched credential producers.
