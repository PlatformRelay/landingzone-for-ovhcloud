## Task text (tasks.md)

T007 [US1] Write credential-set writer tests in tools/internal/live/files_test.go. Requirements: FR-005; ADRs: 0009. Depends on: T004. Cases (given / when / then → defect exposed), per data-model *Credential set*: (1) given an empty account directory / when `WriteCredentialSet` writes the `account-governance` set / then `sets/<instance>/gen-<run_id>/` holds every file at mode 600 and `current` names it → exposes a writer that skips the generation or the pointer. (2) given a previous set / when the writer stops after `SetStepFirstFile` / then a fresh reader loads the previous set whole and the next writer removes the partial generation → exposes files written into live paths. (3) same after `SetStepFiles` and after `SetStepDirSync` → exposes a switch before the generation is durable. (4) same after `SetStepPointerTmp` (just before the rename) → exposes a pointer replaced in place. (5) given the writer stops after `SetStepSwitch` / when a fresh reader loads / then it gets the new set whole → exposes a reader that still prefers the old set. (6) given three earlier generations / when a write completes / then only the current and the previous remain → exposes unbounded growth or removal of the previous generation before the switch. Verify: `task test:live-lane`: every case fails against the stub `WriteCredentialSet`.

## What the tests pin (for T013)

- Layout (data-model *Credential set*, read 2026-10-15): `<Root>/accounts/<Account>/sets/<Instance>/gen-<RunID>/<rel>`, `current` a regular file whose whole content is `gen-<RunID>` (no trailing newline: data-model says "whole content is the name"), `current.tmp` the staging name, directories 0700, files 0600 (`current` and `current.tmp` included). Verified by reading.
- "A fresh reader" is the test's own `csLoad`, written from data-model's reader rule (resolve `current` once, accept `^gen-[0-9A-Za-z-]+$` naming a sibling directory, read every file of the set from that generation through `ReadCredentialFile`). Reading: T013's Verify says T007's cases go green when `WriteCredentialSet` lands, before T014 resolves sets in production, so the cases must not call `CredentialSetPath` (T008/T014). The production reader's preference is T008's case "flat files and a `current` → reads the generation".
- The previous set of every crash case is laid down by hand (`csSeed`, `csPoint`, through `WriteCredentialFile` and `os.WriteFile`), so a case judges the writer alone.
- Case 1 (`fresh-write`): the set directory holds exactly `current` and `gen-<RunID>`; every directory from `sets/` down and every file are checked for mode; nothing in the account directory lies outside `sets/` (`csOnlySets`).
- Cases 2–4 (`crash-after-first-file`, `-files`, `-dir-sync`, `-pointer-tmp`): `WriteCredentialSet(new, step)` returns `ErrInjectedCrash`; the reader loads the previous generation whole; nothing outside `sets/`; after `SetStepPointerTmp`, `current.tmp` is a 0600 file holding the new name (data-model step 3). Then a complete write leaves exactly `current`, the previous generation and the new one (the partial generation and any `current.tmp` gone; "the previous" after the next write is the generation `current` named before it), and the kept previous generation still holds its set whole. A previous generation removed before the switch fails these cases (the reader cannot load it).
- Case 5 (`crash-after-switch`): the reader loads the new set; `current` is a different file from the one before the write (`os.SameFile` on the two `Lstat`s), so a rewrite in place at the switch fails; the previous generation is kept whole. The previous generation's name sorts after the new one, so the disk alone cannot be read correctly by picking by name.
- Case 6 (`keeps-current-and-previous`): three earlier generations, `current` naming the oldest by name and by modification time (a manual rollback, data-model "manual rollback"); after a complete write only `current`, that generation (its set whole) and the new one remain.
- Not covered by T007 (believed, by design of the step boundaries): the flat-file removal on first migration and the reader (T008, T014); `SetStepCleanup` as a crash point (not in the task text; data-model step 5 leaves the new set current either way); whether `fsync` is actually called. Crash injection stops the writer at its own step boundaries and cannot power-cut between `write` and `fsync`, so the controls show ordering (what is on disk at each boundary), not durability. A writer that skips `fsync` but keeps the order passes; T013's guard G18 names the "switch before fsync" mutant, which these cases kill only as an ordering defect. Likewise a writer that unlinks `current` and then renames `current.tmp` into place passes every boundary check (`os.SameFile` included) while leaving a window with no pointer; the single `rename(2)` over `current` is left to review of T013.

## Learnings

Class: guidance.
- A crash-window test that judges only what a reader sees at each boundary passes a writer that rewrites the pointer in place at the switch; compare the pointer's file identity across the switch.
- A retention test has to read the kept generation, not only list it: a cleanup that empties the rollback generation keeps its name.
- Step-boundary crash injection proves ordering, not durability; say so, and leave fsync and single-rename atomicity to the implementation's review.
