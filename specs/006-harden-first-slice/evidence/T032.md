## Design (what the entry does now)

1. `limitsUnavailable(exec.LookPath, userManagerReachable, delegatedControllers(uid))` before anything starts: `/usr/bin/systemd-run` present, `/usr/bin/systemctl --user show-environment` answers within 5 s, the user manager's `cgroup.controllers` (`/sys/fs/cgroup/user.slice/user-<uid>.slice/user@<uid>.service/`) holds `memory` and `pids` as words. Otherwise `LIMITS_UNAVAILABLE <reason>: enable user cgroup delegation (…)` and nothing starts.
2. `systemd-run --user --scope --quiet --collect --unit=lz-offline-<pid>-<random> -p MemoryMax=<bytes> -p MemorySwapMax=0 -p TasksMax=<n> -- <entry> --scope-hold <entry pid> <bwrap> <args…>`, environment `XDG_RUNTIME_DIR=/run/user/<uid>` only (bwrap still `--clearenv`s the child). Only options `TestScopeArgv` admits are used.
3. The scope's first process is the entry itself in `--scope-hold` mode (the holder): it dies with the entry (`PR_SET_PDEATHSIG`, parent pid checked), marks its gate (fd 3) and report (fd 4) close-on-exec so the sandbox sees neither, waits for one byte at the gate and only then runs bwrap with `Pdeathsig` (at end of file it exits 125 and runs nothing), and once bwrap has ended reads the scope's `memory.events`/`pids.events` from inside the scope (which therefore still exists) and writes them to fd 4; its exit code is bwrap's (signals as 128 + n, 125 when it cannot report).
4. The entry waits (≤ 10 s) for the holder to sit in `<unit>.scope`, then `checkScope` (`memory.max`, `pids.max`), `memory.swap.max` = `0`, and both events files readable. On any failure it kills the holder, closes the gate and refuses `LIMITS_UNAVAILABLE limit-not-applied: …`; bwrap was never started. Otherwise it writes the gate's byte. (Until round 2 the gate was bwrap's own `--block-fd`, which goes on at end of file; see *Review*.) This makes `limit-not-applied` a refusal before the child starts, not after (research R5 said "verifies after start").
5. While the child runs, the scope's events files are read every 5 ms, keeping the last successful read (the scope's files go ENODEV once it is empty, T029 finding). The first time `limitTripped` names a limit, the entry writes `1` to the scope's `cgroup.kill` and kills the holder (bwrap and the sandbox follow). A storm that retries after a refused fork is stopped by this, not by `pids.max` (T029 finding).
6. After the holder is reaped, its report decides when the watch saw nothing (a limit hit just before the end); a run with no report is not a pass. `childResult`: a tripped limit is `RESOURCE_LIMIT <memory|tasks> target=<target>` (ahead of the exit error), else `CHILD_FAILED`, exit non-zero via `fail`.

Decisions taken here, with counterpoints:
- `MemorySwapMax=0` plus the swap check (T029 finding): FR-013 names no swap mechanism; without it a host with free swap swaps instead of stopping the child. Counterpoint: a host without swap accounting has no `memory.swap.max` and is refused `limit-not-applied` (fail-closed); believed rare (Ubuntu runners have it, UNVERIFIED until P3).
- The gate goes beyond R5's "verify after start" in the safe direction: FR-013 says "refuses before starting the child" and lists `limit-not-applied` among the refusal reasons.
- `XDG_RUNTIME_DIR` is derived from the uid, not taken from the operator's environment, so nothing of the caller's environment reaches bwrap. Counterpoint: a host whose runtime directory is elsewhere is refused `no-user-manager`.

## Maintainability

1. Duplicates existing code? The host test's scope polling and `scopeWatch` do the same job in two places by design (the test composes the helpers, not the entry).
2. Hard to read? `runLimited` is linear: refuse, start held, verify, release, watch, wait.
3. Hidden coupling? `processScope` and `delegatedControllers` assume cgroup v2 at `/sys/fs/cgroup` and systemd's user slice layout; any other layout is refused (fail-closed), never run without limits.
4. Magic values? 5 ms poll, 10 s scope wait, 5 s systemctl bound, each commented; constants from the peak table.
5. Dead code? None.
6. Error handling weakened? Ignored errors only on best-effort kill paths (`cgroup.kill`, `Process.Kill`), each followed by the other kill.
7. Tests brittle? The fake systemd-run is a `/bin/sh` script (busybox inside the entry); timing bounds are wide (10 s against 0.1 s observed).
8. Scope creep? `scope_test.go` is new (entry wiring needed a test home separate from T029's fixed points); docs changes are pins only.

## Learnings

Class: guidance.
- A start gate must be read by code that tells a byte from end of file, and live in the process the supervisor reaps; bwrap's `--block-fd` goes on at end of file, so closing it after killing any other process is a race.
- A supervisor that needs a cgroup's counters after its last child ends can keep a holder process of its own in the cgroup and have it report from inside; polling a user scope misses events in the last interval before removal.
- A fork-storm probe through Task's shell is not a retrying storm: Go aborts at the thread limit. Use a retrying driver (busybox `watch`) and prove the stop with a control that disables it.
