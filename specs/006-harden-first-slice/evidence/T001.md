## Task text (tasks.md)

T001 Write the Taskfile spec-tracing test `TestTaskfileTracesEverySpec` in tools/cmd/lz-check/main_test.go. Requirements: FR-022; ADRs: 0008, 0019. Depends on: none. Cases: (1) given today's Taskfile.yml / when the test parses the `check:specs` default `SPEC_DIRS` / then every spec directory owning registry keys (`NNN/…`, or spec 001's unprefixed keys) is listed → exposes spec 006 missing from the default trace. (2) given today's Taskfile.yml / when it parses the spec arguments of the `ci-source` command in `test:foundation-ci` / then the same set is listed → exposes CI admitting a 006 target without reading spec 006. (3) given the registry / when it reads the `test:foundation-ci` inputs / then they include the `tasks.md` of every spec `ci-source` reads → exposes a stale digest when 005's or 006's task boxes change. Verify: `task test:traceability`: the three cases fail on today's tree for the stated reasons.

## What the test pins (for T002)

- The owning set is computed, not listed: every key of the registry's `requirements` and `procedures` maps, and every check's `requirements` and `creator`; `NNN/…` → spec NNN, an unprefixed key → spec 001. Today: 001, 005, 006 (verified 2026-10-15, failure lines below).
- Case 1 reads the active `SPEC_DIRS: … default "…"` line of the `check:specs` block; cases 2 and 3 read the active `- go -C tools run ./cmd/lz-check -root .. ci-source …` line of the `test:foundation-ci` block, up to an inline `#` comment. Both patterns are line-anchored (`(?m)^ +`), so a commented-out line or a line in another task is never read. Cases 1 and 2 compare spec numbers (`specs/NNN-…`); `check:specs` and `ci-source` refuse a missing directory themselves. A missing task or line fails the test (`t.Fatalf`), so a reworded Taskfile cannot pass by matching nothing.
- Case 3 requires `<dir>/tasks.md`, or a registry entry above it, in `test:foundation-ci`'s scope or inputs for every directory that task's `ci-source` names (reuses `registryReads` and `covered` of 005 T111).
- Textual parsing, no YAML dependency: `tools/go.mod` has none, and adding one for a test is out of scope (verified by reading `tools/go.mod`, 2026-10-15).
