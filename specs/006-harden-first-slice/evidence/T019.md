## Task text (tasks.md)

T019 [US2] Write retry-budget tests in tools/internal/live/chain_test.go. Requirements: FR-008; ADRs: 0008, 0024. Depends on: T016. Cases (given / when / then → defect exposed): (1) given `newRetryBudget(end, reserve)` / when `admit` is asked for a wait that leaves at least the reserve, and one that leaves less / then true, then false → exposes a wait taken with no time left for the read and listings (`chain.go:616`). (2) given three retained instances each needing one retry / when the leftover check reads them / then all finish within one budget → exposes a fresh backoff per instance (`chain.go:713-717`). (3) given a refused wait / when the check reports / then `blocked waiting-for=<instance>`, never `pass` → exposes a late pass. Verify: `task test:live-lane`: every case fails against the stub. Evidence: `evidence/T019.md`; PR; initial status `not-run`.

## What the tests pin (for T024)

- Case 1 `TestRetryBudgetAdmit/{exactly-the-reserve,fits-but-eats-the-reserve,counts-from-now,larger-reserve,reserve-already-gone}`: each row asks `admit` for one wait that leaves at least the reserve (want true) and one that leaves less (want false), and `admit(end+1s, 0)` (want false). Rule: `end - now - wait >= reserve` (data-model: "admitted only if `remaining − w ≥ reserve`"); exactly the reserve left is admitted, one nanosecond less is not; the time left counts from `now`.
- Clock seam (cases 2 and 3): `retryClock` is the wall clock moved on by `spent` plus every wait taken; `After` takes no real time. The run deadline is `budgetLongRun` (90 min), so the destroy-on-exit has 90 min from the destroy's start today and under FR-002 (T018's `destroyBudget` keeps a longer run deadline); `spent` = 90 min − `left`, so the leftover check has about `left` of its budget. Contract for T024 (in `ChainOptions.stateReadClock`'s comment): the budget's time is `clk.Now()` against the destroy context's deadline, and the waits go through `clk.After`.
- Case 2 `TestChainRetryBudgetShared` (account-bootstrap, account-governance and demo-state each answer their first `show -json` with a 503, then succeed; every first wait `retryWait` 4 min):
  - `all-fit` (a pin today): 30 min left; exit 0, report `pass`, no errors or leftovers, each instance read twice, 3 retry lines, 3 waits totalling at most `left` − 30 s.
  - `third-does-not-fit`: 3 × 4 min + 20 s left. Two waits (at most `left` − 30 s in total), account-bootstrap and account-governance read twice, demo-state once, 2 retry lines, and `retryBlocked` for demo-state.
- Reading of case 2's "then all finish within one budget" (recorded, not a change): FR-008 is "one leftover check shares one retry budget across every retained instance it reads, and a wait is admitted only if the time for the read and the remaining listings is still left after it; otherwise … `blocked`". With three waits that fit, today's code also finishes, so a fresh-backoff defect only shows when the shared budget runs out: the waits taken across the instances stay within one budget with the reserve left, and the instance whose wait does not fit is the one waited for. `all-fit` pins the other side (a budget that is too strict fails it).
- Case 3 `TestChainRetryBudgetRefused` (account-governance answers one 503):
  - `reserve-not-left`: 4 min + 20 s left; the wait fits the time left but leaves 20 s, less than the 30 s reserve floor. Today: taken, then a late pass.
  - `beyond-the-budget`: 2 min left. Today: refused, but a plain `fail` naming no instance waited for.
  - Both: no wait, one read, no retry line, and `retryBlocked`.
- `retryBlocked(stack)`: `leftovers.json` outcome `blocked` with an error carrying `blocked waiting-for=<stack>`; exit not 0; no `LZ-LIVE summary <run> pass` line; a listing after the last retained state read (the reserve kept the time for it).
- Not pinned: the chain's exit code and summary outcome for a blocked check (FR-008 names the check's report only: not 0 and not `pass` is pinned); whether the instances after a refused one are still read; how the reserve is estimated above its 30 s floor (data-model: "from the slowest listing so far").

## Learnings

Class: guidance.
- To exhaust a budget of tens of minutes offline, start a fake clock late (wall clock plus what is already spent) and let its `After` advance it; anchor it to a deadline the test fixes for today and after the paired task (here a run deadline above `DefaultDeadline`).
- A wall-clock row that hangs under a mutant hides the fake-clock cases in the same `go test` binary: run mutants with that row deselected too.
