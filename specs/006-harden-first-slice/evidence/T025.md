## Design (read 2026-10-16, verified)

- `ObserveCanary` (`observe.go`), after the admin's bearer is obtained (no create can happen without it):
  1. `GET …/storage/<name>` with the admin. 404: trap mode `trapRemove`. A 2xx: `trapReport`. Any other error: nothing is set up (no create, no trap, both observations `error`, "canary name not checked").
  2. `Trap.Add` registers the cleanup before the create. It reads the mode (an `atomic.Int32`): `trapRemove` runs spec 005's `deleteCanary`; `trapReport` runs `reportCanary` (one GET: nil on 404, otherwise an error naming the bucket, "existed before its create: not removed, check it by hand"; it never writes); `trapNone` does nothing.
  3. The create. 409: mode `trapNone`, both observations `blocked` ("canary name existed before the run (409): not adopted"). Any other error (5xx, dropped connection): mode unchanged, both observations `error`. Success on a name read as present: both observations `blocked` ("… which answered success: not adopted") and no tenant call, since the run cannot tell a freed-and-recreated name from an idempotent create; the trap reports the bucket. Success on a name read as absent: the KD-1 calls as before.
- Why the read (beyond the dispatch's "register before the create, disarm on a 409"): without it, a create that answers 5xx or drops the connection on a name that existed before the run would leave the cleanup armed, and the trap would remove another owner's bucket and objects; FR-009 says such a name is "never adopted or removed". T020's tests allow a read as long as the create is still sent (`evidence/T020.md`, *What the tests pin*); `TestObserveCanaryNameTaken` still sees the create answered 409. The GET route is in the API schema (`kb/api/v1/cloud.json:58859`, `/cloud/project/{serviceName}/region/{regionName}/storage/{name}`). UNVERIFIED live: its 404 for an absent bucket (spec 005's `deleteCanary` already relies on it) and the create's 409 for an existing name (spec 005 relied on it too). A create that succeeds on an existing name is handled without relying on the 409.
- Judge (`assess`): a new observed value `blocked` (`observedBlocked`). The assertion is `blocked` (`outcomeBlocked`) only when every observation short of the expected value is `blocked`; next to an `error` (or another bad value) or a gap (`violated`/`allowed`) it is a `fail` and the detail lists all of them, so a `blocked` subject never hides behind a pass or KD-1's `known-deviation`. The chain counts any outcome other than `pass` and `known-deviation` as a failed L7 run (`chain.go:899`, read 2026-10-16), so `blocked` never passes a run.
- A taken name whose create answers 5xx observes `error` (assessed `fail`), not `blocked`: stricter than FR-009 asks, never a pass (review round 1 note).
- Not pinned, by design: whether the chain's summary turns a `blocked` assertion into a `blocked` run (FR-009 names the assertion only; `evidence/T020.md`).

2. Change surface: ~85 code lines and ~170 test lines for one requirement; most cover the corners the read adds.

4. Second way: one new observed value and outcome (`blocked`), the word the chain and bootstrap already use for outcomes.

6. Abstraction: `Trap` used as is (no new method; data-model fixes no new symbol for FR-009).
7. Debt for green: no; the read, the report mode and the precedence rule are stricter than T020's tests need and each has its own test.
8. Legibility: two `switch` statements over the read and the create answers and a three-value mode with one comment line each.

Easier: a later `blocked` observation (Object Lock read errors, T026) has a judge path. Harder: one more admin call per run, visible in any call-sequence test.
