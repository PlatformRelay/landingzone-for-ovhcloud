## What the tests pin (for T025)

- "When the collector runs" is read as data-model's FR-009 row: the existing collector's canary (`ObserveCanary`) against the fake API, then the run's `Trap`, as `TestObserveCanaryTrap` does. The chain runs the trap after the destroys and joins its error into the run's failure (`chain.go:308-311`, read 2026-10-16); that wiring is spec 005's and is pinned by `TestObserveChain*/trap-fails`, not by this task's tests. data-model's row says "through `ChainOptions`" while naming `TestObserveCanaryTrap`, which calls `ObserveCanary` and `Trap.Run` directly; this task follows the latter (wording deferred to stage B, review round 2 note).
- Every `TestObserveCanaryCreateError` row: the admin's create arrives with the canary's name already in the trap (FR-009: "registered for removal before its create call"). This also catches a cleanup added once the create has returned (review round 1).
- Case 1 `TestObserveCanaryCreateError/{500,503}-after-create` and `/dropped-after-create`: the create makes the bucket, then answers 500 (503), or closes the connection unanswered (a transport error). After `ObserveCanary` and `Trap.Run`: the trap returns nil and the canary is gone; the trap's calls are the admin's, writing only the canary. Neither observation is `denied` or `allowed` (the tenant made no call; spec 005's `create-fails` row already says so).
- Case 2 `TestObserveCanaryCreateError/500-after-create-{delete,read}-fails`: as case 1, then the trap's admin DELETE (or its GET of the canary) answers 500. The canary still exists and the trap returns an error under the canary's name (`Trap.Run` prefixes every error with the registered name, so this proves an error, not the cleanup's own wording). "Reported as a leftover" is read as that error: it is what the chain turns into a failed run before the leftover check lists (which would list the bucket too).
- Case 3 `TestObserveCanaryNameTaken`: the bucket `lz-bkt-canary-<run id>` exists before the run, holding another owner's object; the admin's create answers 409 (the fake's own conflict, not a forced status).
  - `not-adopted` (a pin today): after `ObserveCanary` and `Trap.Run` the bucket and its object are still there; no call other than the create writes anything; the tenant makes no call.
  - `blocked` (red today): `Assess` of the observations gives `kd1-canary` outcome `blocked`, with and without `shared_state_project`. Today: `fail` (two `error` observations).
- `TestObserveCanaryCreateError/500-without-bucket`: a create that answers 500 without making a bucket arrives with the canary in the trap (red today), and the trap then returns nil and writes only the canary's own name (a trap that fails on a canary that never existed). A trap that sends a DELETE without reading first and ignores the 404 also passes; it touches nothing but the canary's name (review round 2 note).
- Pinned beyond FR-009's words: T025 must still send the create (`TestObserveCanaryNameTaken` requires the 409 answer); a read-before-create that skips it fails the test. FR-009 does not require the create, but a read first races another creator, so the 409 is the safe signal (review round 2 note).
- Not pinned: how T025 disarms the trap on a 409 (a flag, a removal from the trap); which observed value carries `blocked` and the detail's wording (only the assessment outcome is pinned); whether the chain's summary treats a `blocked` assessment as `blocked` (FR-009 names the assertion only).

## Learnings

Class: guidance.
- "Registered before the call" is a claim about ordering: have the fake record the trap (or registry) when the call arrives, or a cleanup added once the call returns passes every outcome-only check.
- An error "after the resource exists" has two shapes, an error answer and a dropped connection; a fake that hijacks and closes the connection covers the second (Go does not replay a POST).
