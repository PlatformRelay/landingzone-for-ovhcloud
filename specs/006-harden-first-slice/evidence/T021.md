T021 [US2] Write Object Lock assertion tests in tools/internal/live/s3check_test.go and tools/internal/live/observe_test.go. Requirements: FR-010; ADRs: 0008, 0009. Depends on: T016. ## What the tests pin (for T026)

- Source of the answer shape: the OVHcloud guide documents `aws s3api get-object-lock-configuration` answering `ObjectLockEnabled: Enabled` and `Rule.DefaultRetention.Mode: GOVERNANCE` with `Days` (`docs.ovhcloud.com` storage-and-backup/object-storage/s3-managing-object-lock.mdx:167-190, local mirror, read 2026-10-16). The wire XML (`<ObjectLockConfiguration>` in the S3 namespace) and the not-found code `ObjectLockConfigurationNotFoundError` are AWS's: believed, UNVERIFIED on OVHcloud (premise P5; the next owner chain run observes it).
- `TestS3CheckerObjectLock` (cases 1–3 through the client and the judge together, as the task says): every row sends one signed GET of `/<bucket>?object-lock` with no body and no other call (a dropped GET may be retried once by Go's transport, so that row allows more than one, all of the same shape). No error carries answer text.
  - `pass`: `governance-days` (60 days), `governance-years` (1 year); the parsed `ObjectLock` is `Enabled`, mode GOVERNANCE (case-insensitive), the period as answered.
  - `fail`: `disabled` (`ObjectLockEnabled` not `Enabled`, a governance rule present), `enabled-element-absent` (rule present, element absent), `absent` (404 `ObjectLockConfigurationNotFoundError`), `compliance`, `no-rule`, `rule-without-period`, `rule-without-mode`.
  - `blocked`: `denied` (403), `server-error` (500), `no-such-bucket` and `404-unrecognised` (a 404 other than `ObjectLockConfigurationNotFoundError` is a read error, not a missing lock; review round 1), `undecodable` (200 with a body that is not the document), `dropped` (connection closed unanswered).
- `TestJudgeObjectLock` (the judge alone): only `Enabled` + GOVERNANCE + `Days > 0` or `Years > 0` passes; a negative period (days or years) fails; a read error is `blocked` even next to a governance configuration. A lowercase mode is not pinned either way.
- `TestObserveChainObjectLock` (case 4, the chain harness with a fake observer, as `TestObserveChainReported`): the chain's `observations.json` `expected["state-bucket-object-lock"]` is exactly the sandbox manifest's two state buckets, `lz-bkt-state` and `lz-demo-bkt-state`, once each. Both observed `holds` → exit 0, `pass`. Not observed at all, one bucket not observed, or one `violated` → exit 1, `fail`, the error naming the assertion and the bucket. One `error` → a failed run (non-zero exit, outcome not `pass`) naming the assertion and the bucket; `fail` or `blocked` left to T026 (review round 1). The rows start from `chainPassing()` with every `state-bucket-object-lock` row removed, so T026 adding the lock rows to that helper keeps these fixtures.
- Not pinned: how T026 reaches the bucket from the collector (which authority's S3 keys, the collector seam), the S3 op's name in the checker's gate, the observed value for an unreadable lock (only the judge's `blocked` and a chain outcome that is not `pass`; T026's collector test should pin a read error observed `error`, not `violated`), and whether the chain's summary turns a `blocked` judge into `blocked` (FR-010 names the judge's outcome only).
- T026 will have to change spec 005 tests as `TEST`-class corrections citing FR-010, because adding an assertion to the L7 set makes every complete set incomplete without it (verified with the `impl` control, *Iterations* 2): `chainPassing` (`observe_test.go`) and the chain harness's default observations need the lock rows; `TestL7Subjects` and `collectComplete`'s count of 10 (`collect_test.go`) need the 11th assertion; `TestCollect` needs the collector to observe it against a fake. Every failure in that run names `state-bucket-object-lock` or the assertion count.

## Learnings

Class: guidance.
- An outcome that is a special case of an HTTP status (a 404 that means "not configured") needs a row with the same status and another code, or a reader of the status alone passes.
- Pin at the chain level only what the requirement fixes: where the requirement names a judge outcome (`blocked`), assert "not pass" at the chain, not today's mapping. Build chain fixtures from the shared passing set minus the new assertion, so the paired task can extend the helper.
