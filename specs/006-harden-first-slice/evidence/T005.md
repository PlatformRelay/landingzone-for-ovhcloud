## Task text (tasks.md)

T005 [US1] Write quiet-binding-error tests in tools/internal/live/hardening_test.go. Requirements: FR-003; ADRs: 0009, 0021. Depends on: T004. Cases: (1) given a fake token endpoint answering 302 with an unparseable `Location` that contains the client secret / when `Bind` runs / then its error and `lz-live`'s stderr contain neither the secret nor the URL and name the call and the status class → exposes the `%w` transport path (`binding.go:54`), since Go's client quotes an unparseable `Location`. (2) given a fake `GET /auth/details` doing the same / when `Bind` runs / then the same holds → exposes the same path on the second call. (3) given a fake answering 200 with a body that fails to decode and contains the secret / when `Bind` runs / then the error does not contain it → exposes the `%w` decode path (`binding.go:63`). (4) given a well-behaved fake / when `Bind` runs / then it binds → exposes an over-eager fix that breaks binding. Verify: `task test:live-lane`: the first three cases fail on today's code for the stated reasons; the fourth passes.

## What the tests pin (for the implementation task)

- `Bind`'s signature is unchanged (data-model *Fixed signatures*, FR-003 row); the tests drive it with `API{HTTP: …}` against an `httptest` server, as data-model says. No stub was needed.
- Case 1 and 2 (`token-redirect`, `auth-details-redirect`; lz-live `token`, `auth-details`): the hostile call answers `302` with `Location: http://evil.example/%zz/<secret>` (`%zz` is no URL escape). The error must not contain any four-character window of the secret, `evil.example` or `%zz`; it must contain the call name (`token endpoint`, `GET /auth/details`, the names `binding.go` already uses) and the status class written `3xx`.
- Reading of "the URL": the redirect target (FR-003: "URLs from redirects"). The request URL of the fake (`http://127.0.0.1:<port>/token`) is not asserted absent: it is the configured endpoint, not answer-chosen text. Believed, to be judged by review.
- Reading of "the status class": HTTP's class notation `3xx` (RFC 9110 §15). Neither plan.md nor data-model.md fixes the wording; the implementation task inherits `3xx` as a fixed point. Go returns no response with the Location parse error (`net/http/client.go:665`, Go 1.27.1, read 2026-10-15), so the implementation has to observe the status itself, e.g. with a wrapping `RoundTripper`; control `fix-sketch` (*Iterations* 2) shows that is enough.
- Case 3 (`token-undecodable`, `auth-details-undecodable`): the hostile call answers `200` with `{"access_token":"\u<secret>","account":"\u<secret>"}`. Go 1.27.1's `encoding/json` quotes at most the escape and four characters after it (`invalid escape sequence \us3cr`; experiment on the host, 2026-10-15, verified); other malformed bodies quote one character or none. So the secret begins with `s3cr` and the assertion is "no four-character window of the secret", not "not the whole secret", which no decode error of today's Go would ever contain.
- lz-live's stderr is observed through `lz-live probe` (`probeWorld`, `apiHook`): `probe.go:156` calls `api.Account` (the same `API.do` path) before `Bind`, and `main.go:177` prints the error as `lz-live: <err>`. `w.noSecret` also walks the run record under `.local`.
- Case 4 (`well-behaved-binds`): a fake answering both calls well binds. Positive control: passes from the start, by design.
- Not covered by T005's cases: FR-003's "names … the next action". The task text does not list it; see *Learnings*.

## Learnings

Class: guidance.
- A windowed (partial) secret check needs a secret with no English in it, or it rejects honest messages (`binding`, `decoding`); shared fixtures with English secrets (`probeSecret`) can be windowed only on their random part.
- Go's JSON decode errors quote at most four characters of the body (`\uXXXX`); a test of a decode-path leak has to check fragments, not the whole secret.
- `mutate.py` copies only `tools/`; tests reading `../../../stacks` or `mise.toml` need a whole-checkout scratch copy (as `t005-006-sketch.py` does).
- Not covered by T005's cases: FR-003's "names … the next action". Proposed: the FR-003 implementation task asserts it, or a test task adds the case.
