## What changed (2026-10-19, verified by reading the diff)

- `objectstore.go`: `S3Store.Get`/`Put`/`PutNew` take `ctx`; `requestWith` builds the request with `http.NewRequestWithContext(ctx, …)`, so a request ends when the caller's context ends and none is sent under an ended one. The 30 s client timeout stays as an outer bound. A cancelled request's error is still `quiet`'s (`<method> <bucket>/<key>: timed out` or `: cancelled`; no body or answer text).
- `publish.go`: `ObjectStore.Get`/`Put` take `ctx`; `Publish(ctx, o)` writes with it; `artifactReader{ctx, store}` is the store as `stacks.ArtifactStore` reads it (`stacks` unchanged).
- `apply.go`: `acted(ctx)` → `selected(ctx)` reads producers' envelopes under the run's context; `stack` adapts its inputs through `artifactReader{ctx, store}` and publishes through the new `laneRunner.publish(ctx, …)`: the envelope's write carries the run's context, and the record is not written once that context has ended, even when the write answered success. The comment on the deferred deadline check is updated.
- `chain.go`: the chain's re-selection, `destroyStack`'s input reads and the L7 second writer's input reads carry the context their step already holds. `destroyStack` is called with `dctx` (the detached destroy budget, FR-002), so its reads carry the destroy budget, not the run's deadline (read: `chain.go:353`, unchanged).
- `observe.go` (`objectCreator.PutNew`, `collector.read`, `stateObjects`, `outputs`, `tenantS3Read`, the lock-contention write and read) and `bootstrap_state.go` (`publish(ctx, keys)`, `unchangedStore.Put`, verify's input read): signature follow-through with the context each already had. The lock trap's `release(ctx)` reads under the trap's own (cleanup) context.
- Docs: `verification-status.md` and `run-the-first-slice.md` say a store request ends at the deadline and nothing more is published; both re-pinned (blobs of `apply.go`, `chain.go`, `observe.go`; `last_verified` 34dff5e).

## Maintainability

1. Duplicates existing code? No; one adapter (`artifactReader`) and one helper (`publish`) that takes the publication steps out of `stack`.
2. Hard to read? No; the context is a parameter at each call; the record gate has its reason in a comment.
3. Hidden coupling? `artifactReader` holds a context in a struct, scoped to one `Adapt` call, so `stacks.ArtifactStore` and `stacks` stay unchanged.
4. Magic values? Test timings reuse `boundedHang`/`boundedSlack`; `boundedStoreGiveUp` is named with its reason.
5. Dead code? None (the redundant gate removed, iteration 3).
6. Error handling weakened? No; a cancelled request is an error where it used to wait up to 30 s; `quiet` unchanged.
7. Tests brittle? The read-inputs row keys on the third read; its fixture check fails if that read does not follow the binding.
8. Scope creep? `observe.go`, `bootstrap_state.go` and `chain.go` change only because the interface does, carrying the context they hold.
Verdict: easier; the run's deadline now bounds the store as it bounds `tofu` and the API.

## Learnings

Class: sensor.
- A signature change of a shared interface compiles under every build tag its test files carry (`go vet -tags offlinetools`): untagged vet and tests passed on a broken tagged build, which only `test:exchange` builds. Proposed: the close-task inner tier for `tools/` vets with `-tags offlinetools` too.
- "No publication after the deadline" needs a row whose store answers success just after its context ends; and a step that returns the context's cause itself meets the run's deferred cause join, so check the error's lines are distinct.
