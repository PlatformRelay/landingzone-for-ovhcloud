## Design (verified 2026-10-20, by reading the code and the pinned toolchain)

- Toolchain: the r5 runtime's `resources/` holds `go`, `task`, `terramate`, `tflint`, `tofu`, a provider mirror and the rootfs; no gocognit or golangci-lint (verified: `ls ~/.local/share/ovh-lz/003-runtime-r5/runtime/resources`). The host's golangci-lint v2.13.1 is built with `github.com/uudashr/gocognit v1.2.1` (verified: `go version -m` on the binary). The score is therefore a port of gocognit v1.2.1's `gocognit.go` and `recv.go` (read from the host module cache, `~/go/pkg/mod/github.com/uudashr/gocognit@v1.2.1/`), cited in `complexity.go`'s header comment with the rules it implements: +1 plus nesting for if/switch/type switch/select/for/range; +1 for else if and else without nesting (an else block's statements stay at the if's level, as in gocognit); nesting rises in those bodies and in function literals; +1 for goto and labelled break/continue; +1 per run of like operators in a `&&`/`||` chain (a parenthesis ends the chain); +1 for a direct recursive call by plain name, compared by `ast.Object` as gocognit does. Function names are gocognit's (`(T).M`, `(*T).M`, type parameters dropped).
- Scope of the score: every `.go` file under `tools/`, tests and build-tagged files included (golangci-lint runs tests by default), except `tools/vendor` and file names starting with `.` or `_` (the go tool never compiles those). Directories named `testdata` or starting with `.` or `_` are scored (round 2 fix): `./...` skips them, but an import can still compile a package there. Today none of them holds a `.go` file (verified 2026-10-20, `find`), so parity is unchanged. Any entry under `tools/` that is neither a regular file nor a directory (a link to a file or to a directory) is an input error, not skipped: the build can import a package through a linked directory (round 1 fix). `//gocognit:ignore` is deliberately not honoured: the baseline is the only exception list.
- Baseline: `<score> <file> <function>` per line, sorted by `<file> <function>` as one string (bytewise), every score over 14, `#` comments and blank lines allowed; the function field must be a name as gocognit prints it (`Name`, `(T).Name`, `(*T).Name`; round 1 fix). A malformed, unsorted or duplicate line, a score at or under 14, or a file that is not a clean `.go` path under `tools/` is an input error (exit 2, naming the line).
- Judgement (key `<file> <function>`): unlisted and over 14 → `COMPLEXITY_NEW` (finding); listed and higher → `COMPLEXITY_ROSE` (finding); lower → `COMPLEXITY_LOWER` (passes); listed but gone → `COMPLEXITY_GONE` (passes); either of the last two prints `rewrite tools/harness/complexity-baseline.txt downwards: …`. The command lets those pass, as the task says; the repository's own `TestComplexityRealTree` requires `lower=0 gone=0`, so the change that lowers a score or deletes a function rewrites the baseline in the same diff and no headroom is left for the score to climb back (round 1 fix). Findings exit 1 with `COMPLEXITY_FAIL findings=N`; otherwise `COMPLEXITY_OK over=N listed=N lower=N gone=N`.
- The key includes the file, so moving a function over 14 to another file reads as a new function (row `moved-file`): the move must bring it under 15, or the baseline line moves with it in a reviewed diff. Keying by package instead would let build-tag variants of one function (`tty_linux.go`/`tty_other.go`) collide. Two functions with one key (only `init` or `_` can share one) are an input error when either is over 14.
- Registry: `test:traceability`'s inputs already list `tools` (T053), which covers every file the command and the real-tree test read (the Go sources and the baseline); no new read outside it. The baseline joins the check's `scope`, so a change to it selects `test:traceability`. `pipelines/github/foundation-runs.json` is not added anywhere. The `tools/harness/` row of the repository map names the new file (`docs:check` holds the map to the tree; no page pins a changed file).
